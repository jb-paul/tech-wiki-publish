NVIDIA·AMD RoCE 레퍼런스 아키텍처 비교

요약과 범위

RoCE 도입은 Ethernet 스위치 선택이 아니라 GPU–NIC–패브릭–collective 전체 조합의 검증이다. NVIDIA는 Spectrum-X의 검증된 구성 조합과 rail/plane 설계를, AMD는 MI3XX 공통 설계 및 NIC·스위치별 구성 가이드를 제공한다. AMD–DriveNets처럼 특정 조합을 검증한 통합 RA도 있으므로, 이를 단순히 NVIDIA의 폐쇄형 대 AMD의 범용 Ethernet으로 나누면 실제 지원 범위를 놓친다.[1][2][5]

이 문서는 공식 설계 주장, 문서에 제시된 검증 범위, 작성자의 도입 권고를 분리한다. 실제 GPU 클러스터에서 측정한 결과는 아니다. 구성 실행 순서는 roce-fabric-configuration-validation을 따른다.

비교에 사용한 문서 기준선

  • NVIDIA: DGX B300 + Spectrum-4 Ethernet SuperPOD RA의 latest 네트워크 장, Spectrum-X Network Operator 26.4.0, 일반 QoS 동작은 Cumulus Linux 5.14. 이 셋을 임의 조합한 하나의 인증 BOM으로 간주하지 않는다.[1][2][3]
  • AMD: MI300X·MI325X·MI350X·MI355X를 다루는 MI3XX Reference Design, Cluster Documentation Hub의 RoCE/멀티노드 가이드. latest는 고정 릴리스가 아니므로 접근일과 raw snapshot을 함께 보존한다.[5][6][7]
  • AMD 통합 사례: AMD–DriveNets System Reference Architecture RF-72513 v1.0, May 2026, MI355X 및 Pollara 400/Thor2 조합. generic MI3XX 지침과 구분한다.[8]

1. 토폴로지: rail과 plane은 다른 축이다

Rail은 여러 서버의 같은 GPU/NIC rank를 동일한 네트워크 경로 그룹으로 모으는 방식이고, plane은 NIC 트래픽을 독립된 패브릭 경로로 나누는 축이다. AMD 공통 문서는 같은 rail 통신의 낮은 지연과 cross-rail 통신의 spine/Infinity Fabric 경유 비용을 설명하며, NVIDIA B300 RA는 rail 정렬에 twin-plane 구성을 결합한다.[1][5]

NVIDIA B300: rail-aligned + twin-plane

  • 문서의 전체 구성은 512 DGX 노드, SU는 64노드 rail-aligned 그룹이다. 동일 rail의 SU 내 통신은 leaf 한 홉으로 연결하고, rail을 넘는 통신 등은 spine을 이용한다.[1]
  • GPU마다 서로 다른 두 plane으로 2×400GbE를 제공한다. 문서는 ConnectX-8의 plane load balancer와 NVIDIA Route 소프트웨어가 경로 선택·부하 분산을 담당한다고 설명한다.[1]
  • 단일 switch/transceiver/cable 장애 시 작업을 중단하지 않고 원래 대역폭의 절반으로 계속 실행할 수 있다는 것이 RA의 주장이다. 두 케이블만 연결하면 달성되는 일반 RoCE 보장이 아니라 해당 NIC·소프트웨어·토폴로지 조합의 기능으로 평가해야 한다.[1]
  • compute, storage, in-band, OOB의 역할을 분리한다. storage 설계에 나오는 약 4:3 oversubscription을 compute fabric 권장치로 가져오면 안 된다.[1]

원문

AMD MI3XX: workload별 tree·rail·hybrid 선택

  • AMD 문서에서 fat tree는 일반적인 대역폭 정의뿐 아니라 한 호스트의 NIC들을 같은 leaf에 연결하는 host attachment, 즉 1-rail의 뜻으로도 사용된다. 따라서 NVIDIA의 full-fat-tree와 AMD의 tree/rail 구분은 같은 분류 축이라고 단정하지 않는다.[5]
  • rail은 큰 ring collective의 같은-rank 통신에 유리하지만, cross-rail은 spine 또는 Infinity Fabric/PXN을 경유한다. tree는 작은 job/replica와 장애 영향 범위, hybrid는 큰 SU와 any-to-any의 균형을 고려하는 선택지다.[5]
  • 공통 BOM에는 Pollara 400, BCM957608(Thor2), 여러 스위치/NOS, RoCEv2가 나열된다. 목록에 있다는 사실은 모든 NIC×NOS×서버 조합의 인증을 뜻하지 않는다.[5]
  • generic BOM의 권장 subscription 표기는 downstream:upstream = 1:1.16이다. 이는 upstream 여유를 둔 설계이지 1.16:1 oversubscription이 아니다. 실제 포트 수와 breakout으로 충족되는지 다시 계산해야 한다.[5]

원문

분석·권고: 데이터 병렬 AllReduce만으로 rail을 선택하지 않는다. MoE AlltoAll, sharded-state AllGather/ReduceScatter, 작은 동시 job과 불리한 rank 배치를 포함해 같은-rail·cross-rail 성능을 비교한다. network-topology와 collective-communication-primitives를 함께 검토한다.

2. 혼잡 제어: PFC를 무조건 켜거나 끄지 않는다

전통적인 lossless RoCE 기준선

AMD RoCE 가이드는 ECN/CNP에 의한 송신률 조절과 RoCE priority의 PFC를 함께 구성하도록 안내한다. Broadcom Thor2 예제는 RoCE DSCP 26, 내부 priority 3, CNP DSCP 48, 내부 priority 7을 사용한다. 이 값들은 해당 예제의 QoS profile이지 Ethernet 전체에 강제되는 상수가 아니다.[6]

Cumulus 5.14 기본 profile은 switch priority 3 → traffic class 3(RoCE), **priority 6 → class 6(CNP)**를 제시한다. 따라서 AMD 예제의 NIC 내부 CNP priority 7과 NVIDIA 스위치 class 6이 다르다는 이유만으로 호환 불가라고 판단해서는 안 된다. 확인 대상은 wire의 DSCP/PCP와 각 장비의 분류·queue·PFC mapping 전체다.[3][6]

Cumulus는 PFC+ECN의 lossless뿐 아니라 ECN 기반 lossy, packet trimming을 사용하는 lossy-multi-tc도 문서화한다. 스위치가 모드를 지원한다는 사실과 Spectrum-X 특정 RA의 검증 모드라는 사실은 다르다.[3]

원문 원문

AMD–DriveNets Pollara: packet-spray 모드별로 다름

RF-72513 §6.3.3–6.3.5는 다음처럼 구분한다.[8]

  • Switch packet spray: switch per-packet dynamic load balancing, 문서 표기 IONIC_RCQ_NUM_PATHS=1, NIC와 switch에 PFC E2E 활성화.
  • NIC packet spray: UDP source port의 entropy를 바꾸고 switch는 flowlet dynamic load balancing, PFC 비활성화. 문서의 IONIC_RCQ_NUM_PATHS=128/255는 원문 표기를 보존한 것으로, slash를 포함한 실행용 값으로 복사하지 않는다. 실제 선택값·plugin 버전은 deployment guide에서 확정한다.
  • Pollara NSCC는 RTT/path-aware 혼잡 제어와 selective retransmission 등을 설명한다. 이를 generic RoCE/DCQCN과 같은 설정 profile로 취급하지 않는다.

분석·권고: 기존 PFC+ECN 기반 RoCE에는 그 profile의 지침을 적용하고, Pollara 특수 transport를 채택할 때만 해당 end-to-end 검증 조합으로 전환한다. “AMD는 PFC가 필요 없다” 또는 “RoCE는 항상 PFC가 필수다”라는 제품 전체 단정은 모두 피한다.

원문

3. NIC 속도·확장 수치·검증 범위를 분리한다

  • NVIDIA B300 RA의 GPU당 두 400GbE 경로와 AMD–DriveNets의 400Gbps Pollara/Thor2 endpoint는 서로 다른 구성이다. RF-72513에 등장하는 800G switch port를 GPU당 800G NIC로 읽으면 안 된다.[1][8]
  • RF-72513 ESE는 64노드/512GPU SU, 8-rail 기반 non-blocking 설계와 4:1 blocking 설계를 별도로 제시한다. generic MI3XX의 1:1.16 BOM 권장과 모순이라기보다 목적이 다른 설계안이므로, 가격 비교 시 동일 subscription 조건을 맞춘다.[5][8]
  • RF-72513은 RCCL 검증에 9노드/72GPU를 사용했다고 명시한다. 대규모 topology capacity 표가 있다고 해서 그 최대 규모의 학습 성능까지 실측했다는 뜻은 아니다. 내부 benchmark라는 한계도 문서에 명시되어 있다.[8]
  • MI3XX generic BOM에 적힌 ROCm 6.33, Linux kernel 5.15 - 6.80은 원문 그대로다. 이 표기만으로 실제 지원 릴리스를 확정하거나 임의로 다른 버전으로 교정하지 않는다. 구매·배포 시 ROCm과 OEM 호환성 표를 별도로 확인한다.[5]

4. 소프트웨어 결합과 운영 경계

Spectrum-X Operator 26.4.0 문서는 RA 2.2 ↔ Operator 26.4.0, RA 2.1 ↔ Operator 26.1.0의 검증 관계를 제시한다. CRD가 여러 RA 값을 받아들여도 모두 같은 수준으로 end-to-end 검증된 것은 아니다. dual/quad-plane swplb는 GA, hwplb는 tech preview로 구분되어 있으므로 B300 하드웨어 기능 설명만으로 Kubernetes 기능의 GA 여부를 추정하지 않는다.[2]

AMD는 NIC 드라이버의 최신 kernel 요구가 ROCm/amdgpu 지원 범위보다 앞설 수 있다고 경고한다. RCCL 테스트 예제에는 NCCL_IB_HCA 등 NCCL 이름의 변수가 쓰이며, bnxt_re* 또는 mlx5_* 같은 실제 RDMA 장치 이름을 사용한다. GPU 제품과 NIC 공급사 선택은 별개다.[6][7]

NVIDIA NCCL 2.21 이상은 RoCE GID를 동적으로 선택하며 문서는 NCCL_IB_GID_INDEX를 설정하지 않도록 안내한다. 반면 AMD 멀티노드 가이드는 GID 3 예제를 제시한다. 이는 서로 다른 라이브러리/문서 범위이므로 한쪽 예제를 다른 쪽의 버전 독립 기본값으로 복사하지 않는다.[4][7]

5. 선택 기준과 실패 모드

아래는 문서 비교로 도출한 권고이며 공급사 성능 보증이 아니다.

  • NVIDIA GPU 신규 구축: Spectrum-X RA의 정확한 서버·NIC·switch·firmware·operator 조합을 먼저 shortlist에 둔다. 통합 검증의 이점을 취하되 공급사 의존, 광모듈 비용, 장애 복구 기능의 라이선스·지원 조건을 계약에서 확인한다.
  • AMD GPU 신규 구축: generic MI3XX를 토폴로지 의사결정에, 선택 NIC/NOS 가이드를 실제 구성에 사용한다. 통합 책임을 줄이려면 RF-72513 같은 검증된 파트너 RA를 비교하되 상세 deployment guide와 지원 책임을 확보한다.
  • 기존 Ethernet 재사용: 포트 속도만 맞추지 말고 buffer/headroom, ECN/PFC, packet ordering, GPU-direct 경로와 광모듈 호환성을 PoC로 검증한다. generic RoCE 동작을 Spectrum-X나 Pollara 최적화 기능과 동일시하지 않는다.
  • MoE·다중 tenant: AllReduce 최대 bus bandwidth보다 AlltoAll tail, cross-rail 혼잡, 작은 job의 성능 저하를 우선 평가한다.
  • 장애 대응: dual-plane, ECMP, packet spraying 각각의 장애 대응 주체가 다르다. NIC port-down과 spine-link flap을 분리 시험하고 job 생존·성능 저하·재수렴 시간을 기록한다.

검증·측정과 미해결 항목

실제 클러스터 적용 전 roce-fabric-configuration-validation의 순서로 시험한다. 이 조사에서는 공급사간 동등 조건 benchmark, 특정 현장 BOM 가격, firmware별 알려진 문제, 전체 인증 매트릭스까지 검증하지 않았다. RF-72513은 상세 deployment guide를 DriveNets에 요청하도록 명시하므로 공개 RA만으로 동일한 튜닝을 완전히 재현한다고 주장할 수 없다.[8]
