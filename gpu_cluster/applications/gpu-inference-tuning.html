GPU 추론 튜닝: vLLM 메모리·요청 수·응답 속도

범위와 읽는 법

LLM 서비스에서 빠른 첫 응답, 끊기지 않는 생성, 많은 요청 처리를 함께 조정하는 가이드다. 시작은 gpu-cluster-tuning-guide, 여러 GPU의 통신은 gpu-communication-tuning을 따른다.

기준은 vLLM v0.30.0의 버전 고정 문서·태그 소스, 접근일 2026-09-30이다. 설치 권장 버전이나 모든 GPU의 검증 조합을 뜻하지 않는다. A=RTX 6000 Ada, B=RTX PRO 6000 Blackwell Server Edition, M=MI355X. GPU별 시작점은 작성자 제안, 실제 최적값은 미검증이다.

  • Prefill: 사용자의 입력을 읽는 계산. Decode: 다음 출력 토큰을 차례로 생성하는 계산.
  • KV cache: 이미 읽은 토큰의 중간 계산값을 저장한 GPU 메모리. 매번 처음부터 계산하지 않도록 돕는다.[30][31]
  • TTFT: 첫 토큰까지 시간. ITL: 출력 토큰 사이 시간. 둘 다 queue 대기·실제 부하와 함께 본다.
  • Preemption: 메모리 등 자원이 부족해 일부 요청 처리를 미루는 것. vLLM V1은 기본적으로 나중에 재계산하므로 지연이 늘 수 있다.[29]

메모리·길이

I01. --gpu-memory-utilization — 이 인스턴스의 GPU 메모리 예산

  • 뜻·적용: 모델 실행에 쓸 GPU 메모리 비율. GPU 계산 사용률을 설정하는 옵션이 아니다.[28][33]
  • 기본값·범위: v0.30.0 기본 0.92, 소스 허용 0 < 값 ≤ 1. 과거 v0.10.2 기본 0.9와 구분한다. KV cache byte 값을 지정하면 그 수동 배분이 우선한다.[33][38]
  • 조정·부작용: 부족한 KV 공간을 늘릴 수 있지만 여유 메모리가 줄어 OOM 위험이 높아진다. 다른 프로세스를 포함한 GPU 전체 예산을 자동 조정해 주는 기능이 아니다.[28]
  • 확인 지표: 시작/실행 OOM, KV 사용량, preemption, 처리량과 p95/p99.
  • GPU별 시작점: A/B/M 모두 해당 버전 기본과 실제 여유 확인. 전용 GPU도 바로 1.0으로 올리지 않는다. 공유/MIG/partition 환경은 별도 예산으로 재측정.

I02. --kv-cache-memory-bytes — KV cache 크기 직접 지정

  • 뜻·적용: GPU마다 KV cache에 줄 byte 수를 고정한다. 자동 산정보다 명확한 메모리 예산이 필요할 때 사용한다.[28][33]
  • 기본값·범위: None=자동 산정. 수동은 양의 byte 크기를 사용하며 상한은 실제 가용 메모리. 공식 코드에는 모든 GPU에 같은 상한 숫자가 없다.[33]
  • 조정·부작용: 지정 시 I01의 비율을 따르지 않는다. 작으면 동시 처리량이 줄고 크면 할당 실패 가능. GPU·다른 프로세스·모델이 바뀌면 이전 값을 재사용하지 않는다.[28][29]
  • 확인 지표: 적용된 cache byte/token 용량, OOM, 재계산, 서비스 지연.
  • GPU별 시작점: A/B/M 모두 None. 모델/환경을 고정한 뒤 필요한 경우만 수동 고정. 다른 GPU에서 얻은 byte 값을 복사하지 않는다.

I03. --max-model-len — 입력과 출력을 합친 최대 길이

  • 뜻·적용: 한 요청의 prompt+output 길이 상한. 서비스가 실제로 지원해야 할 최대 길이를 정한다.[28][35]
  • 기본값·범위: 미지정은 모델 config에서 도출. v0.30.0의 -1/auto는 가용 GPU 메모리에 맞춘 자동 길이 선택 요청. 명시 길이는 모델 지원 한도와 KV 공간을 만족해야 한다.[28][35]
  • 조정·부작용: 필요한 만큼만 지원하면 메모리 부담을 줄일 수 있지만 긴 요청을 거절하게 된다. 길이를 줄인 성능과 기존 전체 기능 성능을 동일 조건으로 비교하지 않는다.[40]
  • 확인 지표: 허용/거절 요청, 실제 입력·출력 길이, cache 여유, TTFT·총지연.
  • GPU별 시작점: A는 특히 메모리 경계 확인. B/M도 모델 최대값을 무조건 선택하지 말고 서비스 요구로 결정. 길이 검증을 강제로 우회하지 않는다.

묶어서 처리하는 양과 cache

I04. --max-num-batched-tokens — 한 실행 단계의 총 토큰 예산

  • 뜻·적용: 같은 단계에서 prefill/decode에 배정할 토큰 수의 상한. “동시 요청 수”나 “요청당 길이”와 다르다.[28][29]
  • 기본값·범위: 실행 방식·장치에 따라 자동 결정. 양의 정수이며 max_num_seqs 이상이어야 한다. chunked prefill을 쓰지 않으면 max_model_len 이상이어야 한다. config 클래스의 2048을 모든 서버의 실효 기본값으로 쓰지 않는다.[34][37]
  • 조정·부작용: 작게 잡으면 decode 간섭을 줄여 ITL에 유리할 수 있으나 prefill 진도가 느려진다. 크게 잡으면 prefill/처리량에 유리할 수 있으나 응답 간격과 메모리를 확인해야 한다.[29]
  • 확인 지표: TTFT와 ITL을 함께, output tokens/s, preemption, peak memory.
  • GPU별 시작점: 아래 조건부 자동값을 기록한 뒤 비교. A/B/M 공통으로 ITL 문제면 더 작은 값, prefill 병목이면 더 큰 값을 후보로 삼되 다른 한계를 지킨다.

I05. --max-num-seqs — 한 실행 단계의 sequence 수

  • 뜻·적용: 실행 batch에 들어갈 sequence 수의 상한. API가 받을 수 있는 전체 대기 요청 수를 제한하는 admission control과는 다르다.[28]
  • 기본값·범위: 자동 결정, 양의 정수. max_num_batched_tokens보다 클 수 없다. config 클래스의 128과 엔진이 결정한 값을 구분한다.[34][37]
  • 조정·부작용: 늘리면 GPU를 더 잘 채울 수 있지만 KV 메모리·지연·preemption이 증가할 수 있다. 낮추면 cache 압박은 줄어도 대기 줄은 길어질 수 있다.[29]
  • 확인 지표: running/waiting 요청, KV 사용률, preemption, 응답 목표 내 처리량.
  • GPU별 시작점: A/B/M 모두 자동값이 최적값이라는 가정 없이 부하 시험. 서버 앞단의 queue 상한·timeout·과부하 거절 정책은 따로 둔다.

I04/I05의 자동값 예시 — 소스 분기를 읽은 해석, GPU 실행 결과 아님: v0.30.0, 일반 GPU API server, 장치 메모리 조회 성공, 사용자 override 없음, throughput mode·batched-DP-MoE 미사용, chunked prefill 지원, 충분한 model length라는 조건에서 다음 초기값 분기를 검토할 수 있다.[37]

  • A: token budget 2048, sequence cap 256.
  • B: token budget 8192, sequence cap 1024.
  • M: token budget 16384, sequence cap 1024.

소스는 GPU 이름 자체보다 70/160 GiB 메모리 경계 등을 사용한다. offline LLM 실행, 짧은 최대 길이, throughput mode, 메모리 분할, 장치 조회 실패 등에서 달라진다. 실제 기동 로그의 최종값이 우선하며 위 숫자는 요청 동시 처리 보장이 아니다.[37]

I06. --enable-chunked-prefill — 긴 입력을 나눠 읽기

  • 뜻·적용: 긴 입력을 작은 조각으로 처리해 진행 중인 decode와 함께 배치한다.[29]
  • 기본값·범위: 엔진은 모델이 지원하면 활성화하는 방식으로 결정한다. bool override가 있지만 모델별 지원을 확인해야 한다.[35][37]
  • 조정·부작용: 켜진 정상 상태에서 I04를 조정한다. v0.30.0 소스는 일부 지원 모델에서 수동으로 끄면 crash/잘못된 출력 가능성을 경고하므로 모든 모델에서 자유로운 on/off 성능 실험으로 안내하지 않는다.[37]
  • 확인 지표: 긴 입력이 섞일 때 TTFT·ITL, 출력 정확성, crash, token budget.
  • GPU별 시작점: A/B/M 모두 모델별 자동 선택 유지. 긴 prefill 문제는 먼저 token budget을 조정한다.

I07. --enable-prefix-caching — 같은 입력 앞부분 재사용

  • 뜻·적용: 여러 요청이 공통 문서·시스템 프롬프트를 앞부분에 공유하면 이미 계산한 KV를 재사용한다.[31]
  • 기본값·범위: 엔진은 모델 지원 여부로 기본 활성화를 결정. config 필드의 True만 보고 모든 모델에서 켜진다고 단정하지 않는다.[33][35][37]
  • 조정·부작용: 반복 prefix가 있어야 효과가 있다. 일반적으로 prefill 시간을 줄이는 기능이지 새로운 출력 토큰의 decode 자체를 줄이는 기능은 아니다.[31]
  • 확인 지표: prefix cache hit/queried tokens, cold/warm TTFT, 전체 처리량. cache hit가 높은 시험만 제출하지 않는다.
  • GPU별 시작점: A/B/M 공통으로 지원 시 자동 선택 유지. 실제 공통 prefix가 얼마나 있는지 확인하고, 사용자 간 cache 분리 정책도 검토한다.

병렬화·정밀도·실행 방식

I08. --tensor-parallel-size — 층 안의 계산을 여러 GPU로

  • 뜻·적용: 가중치를 나눠 GPU당 메모리 부담을 줄인다. 모델이 한 장에 안 들어가거나 KV 공간이 부족할 때 검토한다.[29]
  • 기본값·범위: 1, 1 이상의 정수. GPU 자원뿐 아니라 attention head 수의 나눗셈 등 모델 제약도 맞아야 한다.[35][36]
  • 조정·부작용: 늘리면 더 많은 메모리를 쓸 수 있지만 매 층의 동기화 비용이 증가할 수 있다. 적재에 필요한 최소 TP부터 비교한다.[29]
  • 확인 지표: GPU별 메모리, collective 비중, TTFT/ITL, GPU당/전체 처리량.
  • GPU별 시작점: A/B는 TP=1 가능 시 독립 replica와 먼저 비교. M도 TP=1 가능성부터 보고 분할 시 단일 노드 Infinity Fabric 영역부터 검증.

I09. --pipeline-parallel-size — 층 구간을 여러 GPU로

  • 뜻·적용: 모델 층을 여러 구간으로 나눈다. 한 노드 용량을 넘거나 TP 통신이 불리할 때 비교 후보가 된다.[29]
  • 기본값·범위: 1, 1 이상의 정수. 해당 모델의 PP 지원이 필요하며 GPU 수·층 배치도 맞아야 한다.[35][36]
  • 조정·부작용: GPU당 모델 메모리를 줄이지만 stage 대기·전달 지연·불균형이 생길 수 있다. TP×PP 조합과 replica 수를 혼동하지 않는다.
  • 확인 지표: stage별 대기/메모리, 응답 지연, 통신, 전체 처리량.
  • GPU별 시작점: A/B/M 모두 PP=1 기준. 확장이 필요하면 실제 topology로 TP 대 PP를 비교한다. GPU 제품명만으로 PP를 고정하지 않는다.

I10. --kv-cache-dtype — KV cache 숫자 정밀도

  • 뜻·적용: KV 저장 크기를 줄여 긴 문맥이나 더 많은 요청을 수용하려는 설정이다.[30]
  • 기본값·범위: auto; 보통 모델 dtype을 따르지만 모델별 예외가 있다. 후보 auto/FP8 등은 backend·모델별 제한이 있다. 문서는 CUDA의 e4m3/e5m2와 ROCm의 e4m3 경로를 구분한다.[28][30]
  • 조정·부작용: FP8은 메모리를 줄이지만 정확도·scaling 검증이 필요하다. 모든 정밀도 이름이 모든 GPU에서 되는 것은 아니다. 낮은 dtype이 무조건 더 빠른 것도 아니다.[30]
  • 확인 지표: 긴 문맥 검증 점수, cache 용량, 처리량/ITL, backend 오류.
  • GPU별 시작점: A/B/M 모두 auto 기준 → 지원되는 FP8과 정확도 비교. M에 NVIDIA 전용 형식을 복사하지 않는다. scale calibration 방식까지 기록한다.

I11. --enforce-eager — compile/graph 최적화 끄기

  • 뜻·적용: v0.30.0에서는 compile과 CUDA graph를 끄고 기본 PyTorch 실행을 사용한다. 기동 문제·추가 메모리의 원인 분리에 사용한다.[28][35]
  • 기본값·범위: False, True/False.[35]
  • 조정·부작용: True는 준비 시간을 줄일 수 있지만 steady-state decode 성능이 나빠질 수 있다. 시작만 빨라진 결과를 서비스 전체 개선으로 보고하지 않는다.[29][40]
  • 확인 지표: 최초 준비 시간, graph 추가 메모리, warm decode 성능, 오류.
  • GPU별 시작점: A/B/M 모두 해당 backend의 정상 기본값 False. 오류/메모리 원인 분리 때만 True와 비교하며 설치 버전의 의미를 확인한다.

I12. --quantization — 모델 가중치 정밀도 줄이기

  • 뜻·적용: 모델 저장/실행 메모리를 줄이기 위해 가중치 표현을 바꾼다. KV dtype과 별개의 설정이다.[28][40]
  • 기본값·범위: None이면 모델 config의 quantization 설정부터 확인한다. 없으면 비양자화 가중치로 간주하고 dtype을 따른다. 허용 방법 목록은 버전 registry·모델·GPU/커널 조합에 의해 제한된다.[35][39]
  • 조정·부작용: 적은 메모리와 정확도·변환/복원 비용을 절충한다. None이 언제나 FP16 비양자화라는 뜻은 아니다. bit 수만 같아도 kernel이 다르면 속도가 달라질 수 있다.
  • 확인 지표: 실제 선택 kernel, 가중치+KV+workspace 메모리, 긴 문맥·업무 검증 점수, TTFT/ITL.
  • GPU별 시작점: A/B/M 모두 모델의 지원된 원래 구성을 기준선으로 삼는다. A의 4bit 사례를 B/M에 그대로 적용하거나 B의 FP4 기능을 A에 적용하지 않는다.

관측과 적용 순서

권고: 모델/정확도/최대 길이 → 적재 가능한 TP/PP → 메모리 예산 → token budget와 sequence cap → cache/정밀도 → 고급 backend 조정 순으로 좁힌다. 입력 길이·출력 길이·요청 도착률을 고정한 비교와 실제 길이 분포의 부하 시험을 둘 다 한다.

v0.30.0 metrics의 예: vllm:time_to_first_token_seconds, vllm:inter_token_latency_seconds, vllm:request_queue_time_seconds, vllm:num_preemptions, vllm:kv_cache_usage_perc, vllm:num_requests_waiting. 버전별 이름·단위를 다시 확인하며, cache 사용률 1은 100%다.[32]

범위·실패 조건: OOM, 잘못된 출력, 응답 목표 위반, 거절/대기 증가를 함께 보고한다. speculative decoding, prefill/decode 분리, MoE expert parallelism, 특정 fused attention backend의 모든 설정은 이 기본 가이드 범위 밖이다. 필요한 모델에서 별도 검증한다. 실제 vLLM 서버·GPU 부하 시험은 이 작성 작업에서 실행하지 않았다.
