AMD Instinct MI355X 클러스터 레퍼런스 아키텍처

요약과 범위

MI355X는 288GB HBM3E·8TB/s의 GPU를 8개 연결한 직접 수랭(DLC) 노드를 기본 단위로 검토하고, 노드 내부 Infinity Fabric과 노드 외부 Ethernet/RDMA를 구분해 설계해야 한다. AMD의 공식 microarchitecture 문서는 MI355X를 1400W OAM/DLC 제품으로 설명하며, 같은 계열의 MI350X 공랭 제품이나 PCIe 제품과 구별한다.[1]

이 문서는 사용자 표기 ml355x를 문맥상 AMD Instinct MI355X 요청으로 해석해 작성했다. 기준일은 2026-09-30이며, 제품 사양·공식 설계·작성자 계산/권고·제조사 내부 실측을 구분한다. 자체 하드웨어 벤치마크는 수행하지 않았다.

사용한 레퍼런스의 역할

  • AMD MI3XX Reference Design: MI300X·MI325X·MI350X·MI355X를 포괄하는 네트워크·전력 공통 설계. generic BOM을 MI355X의 완성된 인증 서버 목록으로 취급하지 않는다.[2]
  • AMD–DriveNets System Reference Architecture, RF-72513 v1.0, May 2026: MI355X, Pollara 400/Thor2, ESE/FSE 패브릭, RCCL·추론·학습·장애 시험을 다룬 통합 RA. 문서 표지의 버전/날짜를 사용하며 검색엔진 수집일과 혼동하지 않는다.[3]
  • AMD ROCm microarchitecture 문서 + Supermicro OEM datasheet: GPU 내부 연결·메모리 및 실제 서버의 슬롯·전원·냉각을 교차 확인한다. 조회 당시 ROCm 문서 제목은 10.0.0이지만, 이것을 RF-72513의 실측 소프트웨어 버전으로 대체하지 않는다.[1][6]

원문 원문

1. GPU와 8-GPU 노드의 설계 경계

  • GPU: CDNA 4, 8 XCD·2 IOD, GPU당 288GB HBM3E, peak 8TB/s. MXFP4/MXFP6 등 micro-scaling 형식을 지원한다. 지원 형식이 있다는 사실은 선택 모델·커널이 해당 형식으로 실행된다는 보장이 아니다.[1]
  • Scale-up: 8-GPU fully connected topology. GPU마다 host로 PCIe Gen5 x16, 다른 GPU로 7개 Infinity Fabric link를 연결한다. 공식 문서는 GPU당 aggregate communication bandwidth를 1TB/s 초과로 설명한다.[1]
  • 용량 계산: 8 × 288GB = 2304GB의 HBM 용량 합계와 8 × 8TB/s = 64TB/s의 로컬 메모리 대역폭 합계. 단일 GPU의 로컬 메모리나 노드 외부 네트워크 대역폭이 아니다.
  • 전력: RA의 GPU 사양표는 maximum TBP 1400W, ROCm 문서는 MI355X를 1400W direct liquid-cooled로 구분한다. 실제 OEM power cap과 시설 설계 조건을 별도로 고정한다.[1][3]
  • UBB/OAM: RA는 8개 GPU를 UBB에 구성하며 2U까지 가능한 플랫폼 통합을 설명하지만, 이것은 모든 OEM 서버가 2U라는 뜻이 아니다. 확인한 Supermicro 구현은 4U다.[3][6]

설계 권고: 큰 모델의 TP/EP는 먼저 단일 노드의 Infinity Fabric 영역 안에서 검증하고, 노드를 넘는 DP·sharded-state·MoE 통신은 별도 평가한다. 2304GB를 자동으로 합쳐진 단일 GPU 주소 공간처럼 계획하지 말고 weight·KV cache·activation·optimizer·workspace의 rank별 배치를 계산한다. 메모리 용량만으로 처리량/SLO를 보장할 수 없다.

원문

2. 실제 OEM 구현과 권장 기준 노드

Supermicro AS-4126GS-NMR-LCC — 공식 데이터시트 확인

  • 4U, 최대 8개 MI355X OAM GPU, GPU 간 Infinity Fabric, CPU–GPU PCIe 5.0 x16.[6]
  • Dual AMD EPYC 9005/9004, CPU당 최대 500W와 liquid cooling. DIMM 24개, 최대 6TB DDR5; 최고 메모리 속도는 CPU 세대에 따라 다르다.[6]
  • 확장 슬롯: 8 × PCIe 5.0 x16 LP + 2 × PCIe 5.0 x16 FHHL. 슬롯 수는 실제 NIC 장착·배선·지원 여부와 별개다.[6]
  • 저장장치: front hot-swap 8 × 2.5-inch PCIe 5.0 x4 NVMe bay, 별도 M.2 NVMe slot 2개.[6]
  • 관리 연결: onboard 2 × 10GbE, dedicated BMC 1GbE. onboard 10GbE를 AI backend 400GbE 대신 사용하지 않는다.[6]
  • 냉각: Direct-to-Chip cold plate와 chassis fan을 함께 사용한다. 데이터시트는 liquid cooling에 onsite service가 필요하다고 명시한다.[6]
  • 전원: 4 × 6600W, 2+2 redundant PSU. OEM은 full redundancy가 configuration/application load에 달려 있다고 단서를 붙인다.[6]

RA는 Dell PowerEdge XE9785L도 검증 서버의 일부로 열거하지만, 여기서는 Dell의 전체 current BOM을 직접 검증한 것처럼 다루지 않는다. 다른 chassis/OEM으로 변경할 때는 RF-72513의 부분 목록만으로 GPU·NIC·cooling support를 확정하지 않는다.[3]

작성자 제안: 통신 집약적 workload용 기준선

아래는 공식 자료를 토대로 제안한 설계안이지 별도의 AMD 인증 BOM이 아니다. 8-GPU 서버에 GPU:NIC = 1:1, 8 × 400GbE backend를 우선 평가하고, 정확한 NIC·riser·PCIe switch·광모듈 조합은 OEM 승인 포트맵으로 확정한다. RA의 검증 NIC는 AMD Pensando Pollara 400과 Broadcom BCM57608 Thor2 400이다.[3]

계산: 8 × 400Gb/s = 3.2Tb/s = 400GB/s의 노드당 backend 명목 합계다. 이것은 GPU당 HBM 8TB/s와 다른 경로이며, duplex 합산이나 application bandwidth를 뜻하지 않는다. 예산을 위해 NIC를 공유한다면 rank 배치·PCIe 병목·AlltoAll tail latency를 다시 검증한다.

Host RAM·NVMe 권고: OEM 최대 6TB를 최소 필수 용량으로 쓰지 않는다. CPU preprocessing, data cache, model staging, checkpoint buffer와 장애 복구 목표로 산정하고 socket별 DIMM을 균형 배치한다. GPU–NIC가 같은 PCIe/NUMA 영역에 있는지 확인하라는 AMD multi-node 지침을 따른다.[4]

원문

3. Scale-out 패브릭: generic MI3XX와 DriveNets 구분

A. AMD 공통 MI3XX 설계

generic 문서는 tree·rail·hybrid topology를 비교한다. 동일 rail 통신은 낮은 hop count에 유리하지만 cross-rail은 spine 또는 Infinity Fabric/PXN을 경유할 수 있다. fat tree라는 용어를 host NIC들이 같은 leaf에 붙는 1-rail attachment 의미로도 사용하므로, uplink 대역폭 보장 개념과 구분한다.[2]

generic BOM의 subscription은 downstream:upstream = 1:1.16이다. upstream 여유를 둔 권장 예시이지 1.16:1 oversubscription이 아니다. 128–1024GPU 및 1024–8192GPU BOM은 공급사·설계별 변경을 전제로 한 일반 예시다.[2]

B. DriveNets Endpoint Scheduled Ethernet — ESE

  • RA의 ESE는 Tomahawk 5 기반 2500S, 64 × 800GbE, 51.2Tb/s 스위치와 Pollara 등의 endpoint 기능을 활용한다. 800G switch 포트가 400G NIC를 자동으로 800G endpoint로 바꾸지는 않는다.[3]
  • 64노드 / 512GPU SU를 기본 예시로, 2-tier 및 3-tier 구성을 설명한다. Table 6의 128노드 / 1024GPU 예시는 leaf 16개, spine 8개다.[3]
  • 3-tier non-blocking 8-rail과 spine–super-spine 간 4:1 blocking은 서로 다른 비용·대역폭 설계다. 모델의 cross-POD 통신이 적다는 검증 없이 4:1을 기본값으로 선택하지 않는다.[3]
  • SU=64노드는 해당 DriveNets 예시의 단위이지 MI355X 최소 구매 수량이나 AMD 전체의 고정 SU 규격이 아니다. 소규모는 generic 설계의 작은 topology와 함께 검토한다.[2][3]

C. DriveNets Fabric Scheduled Ethernet — FSE

FSE는 NCP leaf / NCF spine을 사용한다. ingress leaf의 VOQ와 credit scheduling, fabric 내부 cell spraying 및 egress 재조립으로 혼잡과 경로 분산을 다루는 구조이며, Pollara의 NIC packet spraying과 다른 계층이다.[3]

RA Table 12의 512개 400G endpoint 예시는 NCP 16개 + NCF 5개, 800G 포트의 2×400G breakout을 사용한다. GPU당 endpoint 1개라는 설계 가정에서 이를 512GPU에 대응시킬 수 있지만, ESE의 같은 GPU 규모에 이 FSE 장비 수량을 그대로 섞으면 안 된다.[3]

RoCE·혼잡 제어 적용 규칙

  • 일반 RoCE 구성은 vendor 지침의 ECN/CNP + RoCE priority PFC profile을 출발점으로 한다.[5]
  • RF-72513의 Pollara switch packet spray 예시는 PFC E2E 활성화, NIC packet spray 예시는 PFC 비활성화와 flowlet load balancing을 설명한다. NIC/NOS/plugin 조합을 확인하지 않고 “MI355X는 PFC가 필요 없다”고 일반화하지 않는다.[3]
  • 세부 QoS mapping·GID·GPU-direct·collective 시험은 roce-fabric-configuration-validation, NVIDIA와의 설계 비교는 nvidia-amd-roce-reference-architectures를 따른다.

4. 랙·전력·냉각: GPU TBP와 시설 용량 분리

GPU-only 계산: 8 × 1400W = 11.2kW/node; 64노드 SU라면 716.8kW다. CPU·RAM·NIC·NVMe·fan·전원 변환 손실·switch·storage·CDU를 제외한 GPU TBP 합계이며, 실측 평균 소비전력이 아니다.[1][3]

AMD generic 설계는 256개 MI355X DLC system / 2048GPU에 평균 약 14kW/system, 합계 약 3.584MW라는 설계 가정을 제공한다. 문서는 이를 명시적으로 estimate로 한정하며 storage/management의 전력은 OEM과 별도 협의하도록 한다. 따라서 “4MW면 2048GPU 시설 전체가 완성된다”는 결론은 부적절하다.[2]

OEM 전원 검토: Supermicro의 6600W PSU 두 개 기준 명목 용량 계산은 13.2kW다. generic의 14kW 가정을 이 서버의 보장 소비전력으로 옮기거나, PSU 네 개의 합계를 2+2 장애 시 가용 용량으로 보면 안 된다. 실제 full redundancy 조건·입력 전원·power cap·장애 시 derating을 OEM에 확인한다.[2][6]

시설 설계 권고: rack당 서버 수는 U 공간보다 A/B feed 장애 시 허용 전력, CDU 처리 용량, 배관 flow/pressure drop, 공급/환수 온도, 냉각수 품질, leak detection, 정비 공간으로 먼저 제한한다. 위 diagram의 CDU는 논리 기능이며 rack 내/외 배치와 facility loop 조건은 OEM 설계에 따른다. CPU·DIMM·NIC·fan의 잔여 공랭 부하도 열수지에 포함한다.

용량 산정 방법: node·network·storage·management 부하를 합친 IT 전력과, CDU/pump 및 facility overhead의 계측 경계를 명시한다. PUE를 적용할 때 이미 IT 부하에 포함한 냉각장치 전력을 다시 더하지 않는다. power-cooling에서 전력·냉각의 시설 경계를 함께 확인한다.

원문 원문

5. 소프트웨어·스토리지·운영

  • RA 실측 stack: RF-72513 Table 13은 Ubuntu 22.04.5 LTS, AMD GPU driver 6.16.13, ROCm 7.2.0.70200, HIP 7.2.26015, RCCL 2.27.7.70200, Pollara NIC FW 1.117.5-a-45를 기록한다. 재현 기준선이지 모든 신규 설치의 최신 권장 버전은 아니다.[3]
  • 버전 일관성 권고: MI355X 지원 OS/kernel/driver/ROCm, framework·attention/quantization kernel, RCCL·network plugin·NIC firmware·NOS를 한 compatibility manifest로 고정한다. generic BOM의 ROCm 6.33 (Or above) 같은 원문 표기를 임의로 수정하거나 MI355X 지원 보증으로 사용하지 않는다.[2]
  • 관리 계층: DriveNets AI Cluster Orchestrator는 fabric inventory/topology·ZTP·DNOS/firmware lifecycle·fault/telemetry를 설명한다. 이를 Slurm/Kubernetes job scheduling·model serving·GPU partition 관리를 모두 대신하는 제품으로 해석하지 않는다.[3]
  • 스토리지 권고: model/artifact 저장소, shared training dataset, checkpoint, local NVMe cache, control-plane durable state를 분리 산정한다. generic 문서의 제품 예시나 local storage 최소값을 MI355X workload의 throughput SLA로 복사하지 않는다. cold model loading, checkpoint 동시 쓰기 및 실제 복구 시간을 측정한다.[2]
  • Partition 주의: compute partition·memory partition·SR-IOV VM isolation을 구분한다. 최신 microarchitecture 문서는 MI355X의 1/2/4/8 compute partition과 NPS1/NPS2를 설명하지만 RF-72513 GPU 사양표는 memory partitions를 1 or 4로 표기한다. 이 불일치 때문에 contested: true로 표시하며, 실제 지원 모드와 격리 수준은 해당 driver/virtualization release에서 확인한다.[1][3]

6. 공개 검증 범위와 한계

RF-72513 §8.1에 명시된 실측 규모는 다음과 같다. 모두 제조사/파트너 내부 시험이며 독립 재현 결과가 아니다.[3]

  • RDMA bisection: 8노드 / 64GPU.
  • RCCL 및 multi-node inference: 9노드 / 72GPU.
  • Single-node inference: 1노드 / 8GPU.
  • Multi-node training: 8노드 / 64GPU.
  • §11.2 장애 시험: 10분의 RDMA 부하 중 약 5% interface에 5초 link flap을 주는 조건. 이를 PSU/CDU 장애, NIC hard failure, 장시간 training job의 무중단 보장으로 확장하지 않는다.

RA의 수천~수십만 GPU topology 표는 설계상 연결 규모다. 해당 최대 규모의 학습·추론을 모두 실측했다는 증거가 아니다. 또한 RA는 내부 시험의 구성·모델·버전별 결과이며 일반적 성능이나 모든 배포 결과를 보장하지 않는다고 명시한다.[3]

추천: 대규모 도입 결정은 “GPU peak FLOPS”가 아니라 실제 모델의 정확도 조건을 맞춘 tokens/s, TTFT/TPOT, p95/p99, 학습 step time, 장애 포함 job completion time 및 비용으로 판단한다. RTX PRO와의 비교도 rtx-6000-cluster-reference-architecture의 PCIe/GDDR·용도 차이를 반영해 workload별로 수행한다.

7. 도입 전 인수 검증 — 현장에서 실행할 체크리스트

  1. BOM/시설: 정확한 MI355X GPU·UBB·OEM·riser/NIC·광모듈·firmware와 냉각/전원 보증 조건을 고정한다. 원문 1400W와 실제 power cap을 함께 기록한다.
  2. 단일 노드: GPU 8개 inventory, HBM/ECC, Infinity Fabric link, GPU pair별 P2P 대역폭/지연, PCIe 폭·속도, NUMA locality를 확인한다. ROCm partition 변경 전후 장치 노출도 검증한다.
  3. 노드 간: AMD 가이드에 따라 H2H RDMA와 GPU-memory RDMA를 나누어 측정한다. GPU-direct가 아닌 host staging 또는 TCP fallback을 배제하고 모든 GPU–NIC 경로를 시험한다.[4]
  4. Collective 확장: RCCL AllReduce·AllGather·ReduceScatter·AlltoAll을 단일 노드→노드 간→cross-rail/SU 순으로 검증한다. 평균 bandwidth뿐 아니라 tail, error/retry/ECN/PFC와 불리한 rank 배치를 포함한다.
  5. 실제 workload: 모델·정밀도·context·batch·parallelism을 고정해 serving SLO와 학습 scaling을 측정한다. checkpoint/model-load와 backend traffic을 동시에 발생시킨다.
  6. 실패·복구: link/switch/NIC·전원 feed 장애와 냉각 alarm 시의 drain/stop/recovery를 OEM 승인 절차로 시험한다. 파일 checksum과 checkpoint resume까지 확인한다. 안전 인터록을 해제하지 않는다.

이 문서에서 완료한 검증은 공식 자료 대조·계산·인용·위키 구조 검증이며 위 하드웨어 인수 시험의 실행을 의미하지 않는다.
