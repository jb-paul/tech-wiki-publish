GPU 시스템 튜닝: 네트워크·CPU 배치·전력·스토리지

범위와 읽는 법

서버와 스위치 설정은 여러 작업에 동시에 영향을 준다. 프로그램 설정으로 해결할 수 있는지 먼저 확인하고, 장비 설정은 승인된 점검 시간에 작은 시험 환경부터 바꾼다. 시작 문서는 gpu-cluster-tuning-guide다.

A=RTX 6000 Ada, B=RTX PRO 6000 Blackwell Server Edition, M=MI355X. 아래 시작점은 작성자의 시험 제안이며 제품별 최적값 보장이 아니다. 공식 문서 확인일은 2026-09-30. AMD SMI/NVIDIA SMI의 명령 지원은 GPU·드라이버에 따라 다르므로 설치된 도구의 도움말과 실제 장치 조회를 우선한다.[3][4]

쉽게 말하면 NUMA는 CPU마다 가까운 메모리·장치가 다른 구조, QoS는 트래픽을 분류해 처리 순서를 정하는 규칙, ECN은 혼잡 알림, PFC는 특정 종류의 트래픽을 잠깐 멈추는 기능이다.

배치·네트워크 설정

S01. CPU·메모리 affinity — GPU와 가까운 CPU에 배치

  • 뜻·적용: 프로세스를 실행할 CPU와 사용할 메모리 영역을 정한다. GPU–NIC–CPU가 여러 socket에 나뉜 서버에서 중요하다. AMD는 가까운 GPU–NIC와 같은 NUMA 영역의 CPU 배치를 권고한다.[6]
  • 기본값·범위: OS·scheduler·컨테이너가 정한 현재 배치가 기본선. 허용값은 해당 작업에 할당된 CPU ID와 NUMA node ID이며 공통 숫자 기본값은 없다.
  • 조정·부작용: GPU/NIC와 가까운 CPU·메모리를 선택하되 모든 rank를 같은 core에 몰지 않는다. 원격 접근은 줄어도 너무 좁은 CPU 제한으로 데이터 준비가 느려질 수 있다.
  • 확인 지표: CPU별 사용률, 원격 메모리 접근, 입력 대기, GPU-memory RDMA, 전체 작업 시간.
  • GPU별 시작점: A/B/M 모두 실제 연결도 기반. M도 Infinity Fabric이 있다고 CPU·NIC 배치 문제까지 사라지는 것은 아니다. thread 수는 gpu-training-tuning과 함께 조정.

S02. MTU — 한 번에 보낼 수 있는 패킷 크기

  • 뜻·적용: host interface MTU, 스위치 Ethernet frame 한도, RDMA path MTU는 서로 다른 계층의 제한이다. end-to-end 통신이 느리거나 불안정할 때 함께 확인한다.[6]
  • 기본값·범위: NIC/드라이버/NOS/터널 구성별로 다름. 실제 장치의 지원값과 전체 경로의 가장 작은 제한을 확인한다. 9000, 9216, 4096을 같은 전역 설정값으로 취급하지 않는다.
  • 조정·부작용: 승인된 일관된 MTU 구성으로 맞춘다. 한쪽만 크게 올리면 drop·연결 실패가 날 수 있다. 큰 MTU가 모든 짧은 메시지의 지연을 줄이지는 않는다.
  • 확인 지표: RDMA 연결, frame discard, 재전송, 작은 메시지 지연/큰 메시지 대역폭.
  • GPU별 시작점: A/B/M 공통으로 NIC–스위치 경로 지침 사용. GPU 모델만으로 jumbo frame을 켜지 않는다.

S03. DSCP/PCP → queue 매핑 — 올바른 대기 줄로 보내기

  • 뜻·적용: RoCE 데이터와 혼잡 알림(CNP)을 약속된 queue로 분류한다. 이름이 같은 priority 숫자도 장비 내부 의미가 다를 수 있다.[5]
  • 기본값·범위: 공급사 profile의 wire marking과 switch class 매핑을 사용한다. 공통 기본 class/queue 번호는 없다. 각 장비 CLI의 허용 범위를 확인한다.
  • 조정·부작용: 송신 NIC → 모든 switch → 수신 NIC를 하나의 규칙으로 맞춘다. 일부 구간만 바꾸면 RoCE가 일반 트래픽으로 분류되거나 혼잡 알림이 막힌다.
  • 확인 지표: queue별 packet/counter, 실제 marking, CNP 전달, 관리망 영향.
  • GPU별 시작점: A/B/M 모두 GPU보다 NIC/NOS 조합을 기준으로 결정. 다른 RA의 class 번호를 섞지 않는다.

S04. PFC priority / RoCE mode — 어디를 잠깐 멈출지

  • 뜻·적용: lossless profile에서 지정 트래픽의 손실을 줄인다. 잘못 쓰면 주변 작업도 함께 멈출 수 있다.[5]
  • 기본값·범위: Cumulus Linux 5.14의 nv set qos roce 활성화 기본은 lossless지만, 기존 lossy 모드에서 이 명령만 실행해도 전환된다고 가정하지 않는다. 모드와 priority는 해당 검증 profile 기준이다.[5]
  • 조정·부작용: 일반 lossless에서는 지정 RoCE priority만 적용. 모든 priority에 무조건 켜지 않는다. ECN과 함께 본다. PFC-free는 검증된 NIC transport/profile일 때만 선택.
  • 확인 지표: PFC pause 시간, 긴 지연, queue 정체/drop, 여러 작업 간 간섭.
  • GPU별 시작점: A/B는 NIC/NOS 승인 profile. M은 Pollara **NIC spraying(PFC off)**과 **switch spraying(PFC on)**을 구분한다. MI355X라는 이유만으로 PFC를 끄지 않는다.[10]

S05. ECN threshold·buffer·headroom — 혼잡 알림과 여유 공간

  • 뜻·적용: 대기 줄이 얼마나 찼을 때 혼잡을 알릴지, 흐름 제어가 반응하는 동안 얼마나 저장할지 정한다.[5]
  • 기본값·범위: ASIC·링크 속도·케이블 길이·NOS profile별 값. 단위(byte/cell)와 실제 하드웨어 반올림이 달라 공통 byte 기본값을 제시하지 않는다. 제조사 profile과 장비의 실제 반영값을 기록한다.[5]
  • 조정·부작용: ECN 알림을 늦추면 순간 처리량이 좋아 보여도 지연·drop이 늘 수 있다. buffer만 키우면 대기가 길어질 수 있다. 연관값은 하나의 승인 profile로 시험한다.
  • 확인 지표: ECN/CNP, PFC, queue occupancy, discard, p95/p99 지연. ECN=0을 목표로 삼지 않는다.
  • GPU별 시작점: A/B/M 모두 공식 NIC/switch profile 유지. 관측 증거와 vendor 가이드 없이 임계값을 임의 계산·복사하지 않는다.

전력·동작 속도·분할

S06. GPU power limit / power cap — 전력 상한

  • 뜻·적용: GPU가 사용할 수 있는 전력의 상한을 정한다. 전력 비용·발열·성능의 균형을 평가할 때 사용한다.[3][4]
  • 기본값·범위: 장치에서 읽은 default/min/max와 OEM 승인 범위. NVIDIA --power-limit는 장치 min/max 안에서 설정한다. AMD SMI 문서의 CLI 출력 예시 max cap: 550 W는 MI355X의 상한값이 아니다.[3][4]
  • 조정·부작용: 현 cap을 기준선으로 잡고 허용 범위 안에서 단계적으로 낮춰 비교한다. 낮출수록 성능/W가 무조건 좋아지는 것은 아니다. 최대 제품 전력으로 올리는 것을 첫 튜닝으로 삼지 않는다.
  • 확인 지표: 처리량·지연·완료 시간, 측정 구간 에너지, 온도/throttling, node 전체 전력.
  • GPU별 시작점: A 300W, B 최대 600W configurable, M 1400W는 제품 설명 수치이지 여기서 적용할 권장 cap이 아니다. 각 OEM 현재 cap 유지에서 시작하며 M은 냉각/전원 승인 조건을 우선한다.[7][8][9]

S07. GPU clock / performance mode — 동작 속도 정책

  • 뜻·적용: 자동으로 변하는 GPU 동작 속도를 제한하거나 고정한다. 반복 측정의 변동 원인이나 전력 제한을 분석할 때 쓴다.[3][4]
  • 기본값·범위: 장치의 현재 자동 정책을 기준으로 삼는다. 허용 MHz/clock level은 실제 GPU와 도구가 보고한 목록. 다른 GPU의 MHz 값을 재사용하지 않는다.[3][4]
  • 조정·부작용: 전력·냉각 문제부터 고친 뒤 시험한다. 속도 고정은 발열/소모 전력을 늘리거나 idle 효율을 낮출 수 있고, cap에 걸리면 기대 속도가 유지되지 않을 수 있다.
  • 확인 지표: 실제 clock, 제한 원인, 장시간 처리량, 온도, 에너지/작업.
  • GPU별 시작점: A/B는 자동 정책 유지; 지원되는 경우에만 NVIDIA clock 제어 비교. M은 AMD SMI의 조회된 지원 모드만 사용. BIOS·thermal 보호 기능은 끄지 않는다.

S08. GPU partition — 한 GPU를 여러 작업에 나눠 주기

  • 뜻·적용: 여러 작업의 분리·공유 효율을 높이기 위한 구성이다. 단일 큰 작업을 자동으로 빠르게 하는 옵션이 아니다.[8][9]
  • 기본값·범위: 현재 OEM/driver 구성 기준. B 제품은 최대 4 MIG instance를 설명하지만 실제 profile은 설치 조합에서 조회한다. M은 compute partition과 memory partition을 따로 확인한다. ROCm 문서와 RA의 memory partition 설명이 달라 단일 범위를 확정하지 않았다.[8][9][10]
  • 조정·부작용: 작업을 다른 곳으로 이동한 뒤 변경한다. 보이는 GPU 수·메모리·통신·scheduler resource가 바뀌므로 모델 적재와 통신부터 재시험한다.
  • 확인 지표: instance별 처리량/메모리, 다른 작업의 영향, 전체 서버 처리량, 재시작·복구.
  • GPU별 시작점: A는 B의 MIG 기능을 적용하지 않는다. B/M은 단일 작업 기준선과 여러 작업 공유 시험을 분리. M의 compute/memory partition을 VM 보안 격리와 동일시하지 않는다.

저장장치

S09. 데이터 읽기 동시성·prefetch·local cache

  • 뜻·적용: 데이터를 미리 읽고 가까운 저장장치에 두어 GPU가 입력을 기다리는 시간을 줄인다. DataLoader의 구체적인 설정은 gpu-training-tuning에서 다룬다.
  • 기본값·범위: worker/prefetch의 프레임워크 기본값과 파일시스템 현재 설정을 기준으로 시작. cache 용량·파일 수·대기 중 요청 상한은 실제 RAM/NVMe 여유 내에서 정하며 제품 공통값은 없다.
  • 조정·부작용: 읽기 동시성을 조금씩 늘리고 반복 사용 데이터만 cache한다. 과도한 prefetch는 RAM 부족·shared storage 경합을 부른다. cache hit가 높은 시험과 최초 읽기를 섞지 않는다.
  • 확인 지표: input wait, 실제 읽기 처리량/지연, 메타데이터 요청 수, cache hit, 다른 job 영향.
  • GPU별 시작점: A/B/M 모두 GPU 장수보다 소비하는 데이터량 기준. B/M의 큰 메모리가 공유 저장장치의 속도를 높여주지는 않는다. 세부 설계는 storage-solutions.

S10. Checkpoint 저장 간격·동시 쓰기·stripe

  • 뜻·적용: 학습 상태 저장 때문에 멈추는 시간과 장애 후 다시 계산할 양을 절충한다. stripe는 한 파일을 여러 저장장치에 나누는 방법이다.
  • 기본값·범위: 학습 코드의 checkpoint 정책과 파일시스템별 stripe/count/size가 출발점. 공통 기본값·허용 범위는 없으며 실제 저장장치 제품 지침이 필요하다.
  • 조정·부작용: 비동기 저장/동시 쓰기를 늘리면 잠깐의 정지는 줄 수 있지만 RAM·I/O 경합이 늘 수 있다. 저장 간격을 늘리면 장애 시 재작업이 늘어난다. write 반환과 내구성 확보를 구분한다.
  • 확인 지표: 저장으로 늘어난 step time, checkpoint 완료 시간, 실제 재시작 시간, 파일 무결성.
  • GPU별 시작점: A/B/M 모두 측정한 checkpoint 크기·복구 목표로 결정. 큰 모델의 M은 메모리 용량만 보고 checkpoint 요구를 무시하지 않는다. 상세 원리는 common-pitfalls.

S09/S10은 범용 설계 권고다. 특정 저장장치를 조회·시험한 결과가 아니므로 stripe의 숫자 권장값은 미확정으로 남긴다.

변경 전 확인과 되돌리기

조회용 예시다. 명령이 없는 시스템에서는 설치를 자동 진행하지 말고 관리자에게 도구/권한을 확인한다.

설정 변경은 여기서 실행하지 않았다. 변경 전 값과 readback, backup, 담당자, 점검 시간을 기록한다. ACS/IOMMU off, ECC 해제, thermal protection 해제, 모든 GPU 일괄 partition 변경을 빠른 튜닝 방법으로 제공하지 않는다. AMD 문서도 VM 장치의 ACS/AER 요구를 구분하므로 보안·격리 요구를 먼저 확인한다.[6]

되돌림 조건 권고: 데이터 오류, 지속 drop/hang, 새 냉각 경고, 서비스 지연 목표 위반, 다른 작업의 성능 저하가 발생하면 이전 값 복원 → 실제 값 조회 → 기준 시험 재실행. 네트워크 변경은 양쪽 endpoint와 switch의 정책을 함께 복원한다.
