GPU 학습 튜닝: 배치·병렬화·정밀도·DDP

범위와 읽는 법

학습 속도는 정확한 업데이트를 얼마나 빨리 수행하는지로 평가한다. loss(학습 오차)나 검증 점수가 나빠졌는데 step만 빨라진 것을 같은 품질의 개선으로 보고하지 않는다. 시작은 gpu-cluster-tuning-guide, 데이터 입력·컴파일은 gpu-input-compiler-tuning에서 다룬다.

A=RTX 6000 Ada, B=RTX PRO 6000 Blackwell Server Edition, M=MI355X. 아래 시작점·비교 후보는 작성자의 제안이며 실측 최적값이 아니다. 공식 기본값은 PyTorch 2.14 / v2.14.0 소스, 병렬도 예시는 Megatron Core core_v0.19.2, DeepSpeed는 접근일 2026-09-30의 웹 문서 기준이다.[11][19][26]

gradient는 모델을 어느 방향으로 고칠지 나타내는 값, activation은 계산 중간에 생기는 값이다. DDP는 모델 복사본끼리 gradient를 맞추는 방식이다. DDP 자체가 입력 데이터를 나눠 주지는 않으므로 rank별 데이터 분할을 먼저 확인한다.[11]

배치와 모델 나누기

T01. Microbatch — 한 번에 계산하는 샘플 수

  • 뜻·적용: 한 DP 복사본이 한 번의 forward/backward에서 처리하는 양. 메모리 부족 또는 계산 효율이 낮을 때 조정한다.
  • 기본값·범위: 모든 trainer에 공통인 기본값은 없다. PyTorch DataLoader.batch_size=1은 loader 기본값일 뿐이다. Megatron 학습은 양의 micro_batch_size 지정을 요구한다. 일반 batch는 양의 정수, batch_size=None은 별도의 자동 batching 해제 기능이다.[12][25]
  • 조정·부작용: 메모리 여유 안에서 늘려 계산 효율을 비교한다. activation 증가·OOM 위험이 있고, 누적 횟수를 그대로 두면 전체 학습 배치도 바뀐다.
  • 확인 지표: 유효 samples/tokens/s, peak memory, optimizer update 시간, 검증 점수.
  • GPU별 시작점: A는 특히 메모리 여유를 확인. B/M도 작은 안전값부터 증가. GPU 메모리 비율만큼 배치를 늘리는 고정 공식을 쓰지 않는다.

T02. Gradient accumulation / DDP.no_sync() — 작게 여러 번 계산해 모으기

  • 뜻·적용: microbatch를 K번 계산한 뒤 모델을 한 번 업데이트한다. 중간 통신은 no_sync()로 미룰 수 있다.[11][16]
  • 기본값·범위: 순수 PyTorch loop에는 공통 K 기본값 없음. DeepSpeed gradient_accumulation_steps 기본 1, 양의 정수. DDP는 기본 동기화하며 no_sync()는 인자 없는 context manager다.[11][19]
  • 조정·부작용: 제안 비교는 K=1 기준 → 필요 시 2/4. no_sync() 안에 forward도 넣고 마지막 microstep은 정상 동기화한다. 업데이트 전 전체 gradient가 동기화되어야 한다.[11]
  • 확인 지표: K개 전체 구간의 update 시간, 통신 횟수, 정확성, 글로벌 배치와 수렴. microstep 하나의 속도만 비교하지 않는다.
  • GPU별 시작점: A/B/M 모두 메모리 제약과 목표 글로벌 배치로 결정. A의 작은 microbatch를 보완할 수 있으나, 누적만으로 한 microstep의 계산 효율이 커지지는 않는다.

배치 관계: 같은 크기의 microbatch·평균 loss·균등 DP라면 글로벌 배치 = microbatch × K × DP 복사본 수. TP/PP까지 쓰면 마지막 항은 전체 GPU 수가 아니다.[16][25] 길이가 다른 샘플·마지막 불완전 batch는 실제 유효 sample/token 수로 가중치를 맞춘다. BatchNorm 등을 포함해 큰 배치 한 번과 항상 동일하다고 가정하지 않는다.

T03. DP degree — 같은 모델 복사본 수

  • 뜻·적용: 같은 모델이 서로 다른 데이터를 계산하고 결과를 합친다. 모델이 각 replica에 들어갈 때 처리량 확장에 사용한다.[11]
  • 기본값·범위: DDP process_group=None은 기본 전체 process group 사용이지 DP=1을 뜻하지 않는다. 양의 실제 group 크기로 결정하며 DP만의 보편 상수 기본값은 없다.[11]
  • 조정·부작용: 복사본이 늘면 데이터 처리량과 gradient 통신이 함께 늘어난다. 순수 DDP는 모델 상태를 자동 분할하지 않는다. 글로벌 배치 고정/replica당 배치 고정 시험을 나눈다.
  • 확인 지표: 확장 효율, 가장 느린 rank, 입력 중복/누락, 통신 대기, 수렴.
  • GPU별 시작점: A/B/M 모두 단일 replica 정상 동작 확인 후 확장. 노드를 넘을 때 gpu-communication-tuning을 함께 검증한다.

T04. TP degree — 층 안의 계산을 나누기

  • 뜻·적용: 한 층의 큰 tensor를 여러 GPU가 나눠 계산한다. 모델 메모리가 한 GPU에 들어가지 않을 때 검토한다.[26]
  • 기본값·범위: Megatron Core 해당 태그 tensor_model_parallel_size=1. 양의 병렬도이며 world size·모델 분할 제약을 만족해야 한다. 다른 framework의 기본값으로 일반화하지 않는다.[25][26]
  • 조정·부작용: GPU당 메모리는 줄지만 층마다 통신과 작은 연산의 비용이 늘 수 있다. 필요한 최소 분할부터 비교한다.
  • 확인 지표: rank별 peak memory, 연산/collective 시간, 전체 update 시간.
  • GPU별 시작점: A/B는 PCIe 경로 비용을 확인. M은 가능하면 단일 노드 Infinity Fabric 안에서 먼저 비교. GPU별 고정 TP=4/8을 최적값으로 두지 않는다.

T05. PP degree / pipeline microbatches — 층 구간을 나누기

  • 뜻·적용: 앞/뒤 층을 서로 다른 GPU에 배치하고 작은 batch들을 순서대로 보낸다. 쉬는 시간인 pipeline bubble과 stage 불균형을 줄이는 것이 중요하다.[26][27]
  • 기본값·범위: Megatron pipeline_model_parallel_size=1, virtual pipeline 기본 None. PyTorch ScheduleGPipe의 n_microbatches는 명시 입력이며 stage/schedule 제약을 따른다. accumulation K와 항상 같은 설정이 아니다.[26][27]
  • 조정·부작용: microbatch를 더 잘게 나누면 idle 구간을 줄일 수 있으나 연산 효율·activation buffer·통신 비용이 달라진다. PyTorch PipelineStage는 정해진 shape/dtype과 실제 입출력이 일치해야 한다.[27]
  • 확인 지표: stage별 busy/idle, 최대 stage 시간, 메모리, 전체 update 시간.
  • GPU별 시작점: A/B/M 모두 PP=1이 가능한지 먼저 확인. 필요한 경우 stage별 계산량을 맞추고, TP와 PP를 동시에 무작정 늘리지 않는다.

정밀도와 메모리

T06. Autocast dtype — 연산별 숫자 정밀도 선택

  • 뜻·적용: 필요한 연산은 높은 정밀도를 유지하고 나머지는 낮춰 계산·메모리 비용을 줄인다.[15]
  • 기본값·범위: autocast 호출 시 dtype=None, enabled=True; 문서의 CUDA 기본 dtype은 FP16, CPU는 BF16. BF16은 GPU autocast의 기본값이 아니다. 후보 float16/bfloat16은 장치·연산 지원 조건이 있다.[15]
  • 조정·부작용: 지원 확인 후 BF16을 시험 후보로 삼고 FP32 또는 기존 정밀도와 비교한다. FP16은 작은 값 소실/큰 값 overflow에 주의. forward/loss만 autocast로 감싸고 backward는 밖에서 수행한다.[15]
  • 확인 지표: loss/gradient의 NaN·Inf, 검증 점수, 수렴, 메모리, 처리량.
  • GPU별 시작점: A/B/M 모두 지원되는 BF16을 우선 비교 후보로 검토하되 검증 전 채택하지 않는다. FP8은 별도 모델·kernel·recipe 검증이 필요하며 이 API의 공통 스위치로 설명하지 않는다.

T07. GradScaler — FP16의 작은 gradient 보호

  • 뜻·적용: gradient가 너무 작아 0이 되는 문제를 줄이도록 loss를 확대했다가 업데이트 전에 줄인다.[15][22]
  • 기본값·범위: 호출 기본 enabled=True, init_scale=65536.0, growth_factor=2.0, backoff_factor=0.5, growth_interval=2000. 소스는 growth>1, backoff<1을 검사한다. 운영 후보는 양의 scale/interval·양의 backoff로 제한하되 문서에 없는 전체 hard range를 만들지 않는다.[22]
  • 조정·부작용: FP16은 기본값 유지부터. BF16은 기본 시험에서 scaler 없이 시작하며 dtype에 따라 자동으로 꺼진다고 가정하지 않는다. BF16은 loss scaling이 필요하지 않다고 DeepSpeed 문서가 설명한다.[19]
  • 확인 지표: scale 변화, 건너뛴 optimizer update, NaN/Inf, 실제 성공 update 수.
  • GPU별 시작점: A/B/M 공통으로 dtype 기준. K개 누적 중 scale을 바꾸지 말고, 다 모은 뒤 unscale/clip/step/update한다.[16]

T08. Activation checkpoint use_reentrant — 저장 대신 다시 계산

  • 뜻·적용: 중간 결과 일부를 저장하지 않고 backward에서 다시 계산한다. 메모리가 부족한 block에 선택 적용한다.[14]
  • 기본값·범위: API 기본 None, 명시값 True/False, 공식 권장은 False 명시. v2.14.0 소스의 미명시 경로는 경고 후 True 대입이다. 문서에는 여전히 “2.9부터 예외” 예고가 있어 문서/소스가 불일치한다.[14][23]
  • 조정·부작용: 우선 checkpoint 없음과 use_reentrant=False를 같은 microbatch에서 비교. 메모리는 줄지만 재계산 시간이 든다. 재계산 중 전역 상태·분기가 달라지면 gradient가 틀릴 수 있다.[14]
  • 확인 지표: peak memory, 추가 계산 시간, gradient/검증 점수, 이후 배치 확대 가능성.
  • GPU별 시작점: A/B/M 모두 메모리 병목일 때만 선택. M의 큰 메모리라도 모델 조건에 따라 필요하고, 무조건 켜는 기본 최적화는 아니다.

DDP 세부 설정

T09. bucket_cap_mb — gradient를 묶어 보낼 크기

  • 뜻·적용: 여러 gradient를 한 통신 묶음으로 만들어 계산과 전송을 겹친다.[11]
  • 기본값·범위: API None, 실효 기본 25 MiB. 공식 최소/최대는 미명시. 양의 정수 MiB를 비교 후보로 삼는다. None과 명시적 25는 첫 bucket 처리까지 완전히 같다고 보장하지 않는다.[11][20]
  • 조정·부작용: 제안 후보 10/25/50 MiB. 작으면 일찍 보내지만 호출 횟수 증가, 크면 묶음 효율이 좋아져도 준비 대기 증가. bucket_cap_mb_list와 동시에 강제하지 않는다.[20]
  • 확인 지표: backward 끝에 남은 통신, AllReduce 수/크기, update 시간.
  • GPU별 시작점: A/B/M 모두 None 기준선. GPU 종류만 보고 큰 bucket을 선택하지 않는다.

T10. gradient_as_bucket_view — gradient 저장공간 공유

  • 뜻·적용: gradient가 통신 bucket 저장공간을 공유해 메모리 중복을 줄인다.[11]
  • 기본값·범위: False, True/False.[11]
  • 조정·부작용: True를 비교하되 gradient의 detach_() 등 optimizer 동작을 확인한다. 첫 iteration 뒤 메모리를 측정한다. zero_grad(set_to_none=True) 등에 따라 복사가 완전히 없어지는 것은 아니다.[11]
  • 확인 지표: peak allocated/reserved memory, update 시간, optimizer 호환성.
  • GPU별 시작점: A/B/M 모두 False 기준 → 메모리 병목이면 True 후보. 정확성 검증 후 유지.

T11. static_graph — parameter 사용 방식이 고정인가

  • 뜻·적용: 사용하는/사용하지 않는 parameter 집합과 학습 흐름이 반복마다 바뀌지 않을 때만 적용한다. 입력 크기만 같다는 뜻이 아니다.[11]
  • 기본값·범위: False, True/False.[11]
  • 조정·부작용: 조건이 맞으면 반복 탐색을 줄일 수 있다. 동적 분기 모델에 강제로 켜지 않는다. DDP의 can_set_static_graph 로그는 참고 힌트이지 모든 입력에 대한 증명은 아니다.[11]
  • 확인 지표: 대표 분기별 gradient/오류, CPU 탐색 비용, update 시간.
  • GPU별 시작점: A/B/M 모두 False. GPU가 아닌 모델의 실행 조건으로 True 가능 여부를 결정.

T12. find_unused_parameters — 쓰이지 않은 parameter 찾기

  • 뜻·적용: loss로 이어지지 않아 gradient가 생기지 않는 parameter를 찾는다. 조건부 모델에서 필요할 수 있다.[11]
  • 기본값·범위: False, True/False.[11]
  • 조정·부작용: 불필요한 True는 탐색 비용을 늘리지만, 필요한 True를 속도 때문에 끄면 안 된다. static graph 조건과 함께 판단한다.
  • 확인 지표: 모든 대표 분기의 backward 성공, gradient 유무, update 시간.
  • GPU별 시작점: A/B/M 공통으로 모델의 실제 parameter 사용에 맞춘다. False 기본값이 모든 모델의 안전값은 아니다.

운영·측정 주의

ROCm용 PyTorch도 torch.cuda 인터페이스와 device="cuda"를 재사용한다. M용 코드라고 device="hip"으로 바꾸지 않는다. 이것이 모든 CUDA 전용 최적화의 AMD 지원을 뜻하지는 않는다.[24]

GPU 실행은 비동기라 단순 CPU timer만으로 kernel 시간을 재면 틀릴 수 있다. 전체 작업 구간의 경계 동기화와 GPU event 측정을 목적에 맞게 사용하되, 매 연산을 동기화해 실제 겹침을 없애지 않는다.[17] 짧은 profiler 구간으로 원인을 찾고 최종 처리량은 profiler 없는 실행에서도 확인한다.[18]

범위: FSDP/ZeRO의 세부 sharding/offload bucket, MoE의 expert parallelism, FP8 recipe 전체를 이 문서에서 완전하게 다루지는 않는다. 해당 방식이 필요하면 distributed-training-frameworks와 설치 버전 지침으로 확장하며, DDP 설정을 그대로 복사하지 않는다.
