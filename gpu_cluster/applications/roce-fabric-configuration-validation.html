GPU 클러스터 RoCE 구성 및 검증 가이드

정의·범위

NVIDIA/AMD GPU 클러스터의 RoCE scale-out 경로를 단계별로 검증하는 운영 설계다. 실제 장비에서 실행한 기록이 아니며, 아래 명령은 설치된 NOS·드라이버·perftest 버전을 확인한 뒤 사용하는 예시다. 제품 선택 및 rail/plane 비교는 nvidia-amd-roce-reference-architectures에서 다룬다.

핵심은 IP 연결 성공 → RDMA host-memory → GPU-memory → 동시 NIC → collective → 실제 workload를 분리하는 것이다. NVIDIA는 host/GPU memory 경로와 대역폭/지연 진단을, AMD는 H2H/D2D 및 다중 NIC 장시간 검증을 제시한다.[4][7]

1. 설계 입력과 변경 전 기록

운영 권고: 다음을 한 개의 변경·검증 기록으로 묶고, canary 노드/leaf에서 시작한다.

  • GPU/OEM 서버, NIC ASIC·PCI ID·firmware, 케이블/광모듈, switch ASIC·NOS, host kernel, CUDA/ROCm, NCCL/RCCL와 network plugin 버전.
  • GPU rank → PCIe BDF → NUMA → RDMA HCA → netdev → leaf port → rail → plane 매핑.
  • NIC당·GPU당 단방향 명목 속도, leaf downlink/uplink 합계, SU 경계, oversubscription 정의. 양방향 합계와 collective bus bandwidth를 같은 수치로 비교하지 않는다.
  • compute/storage/bootstrap/OOB 분리 정책, IP/VLAN/VRF/MTU, 사용 transport와 혼잡 제어 profile.
  • 정상 상태 baseline, 설정 backup, 변경 승인·rollback 조건, 장애 주입 테스트 창.

AMD는 NIC driver가 요구하는 kernel과 ROCm/amdgpu 호환성을 확인하도록 안내한다. latest driver를 전체 호환성 검증 없이 자동 적용하지 않는다.[6]

2. QoS 계약을 먼저 확정한다

전통적인 RoCE/DCQCN profile에서는 송신 DSCP/PCP → switch priority → queue/traffic class → PFC priority group → receiver CNP → sender 반응을 경로 전체에서 연결해야 한다. AMD의 Thor2 예제와 Cumulus의 내부 class 번호가 같지 않으므로 wire marking과 내부 번호를 별도로 기록한다.[3][6]

  • RoCE data와 CNP에 어떤 DSCP/PCP를 쓰는지 정한다. NIC와 switch가 같은 packet을 의도한 class로 분류하는지 packet/counter로 확인한다.
  • lossless profile은 RoCE class에 PFC를 적용하고 ECN/CNP 동작을 함께 확인한다. 관리 트래픽까지 모든 priority를 무차별 pause 대상으로 삼지 않는다.
  • ECN threshold·headroom·queue buffer는 ASIC, 속도, 케이블 거리 및 지원 profile에 맞춘다. Cumulus는 ASIC 사이에 RoCE 설정을 그대로 이식하지 말라고 경고한다.[3]
  • NIC MTU·switch Ethernet frame 한도·RDMA path MTU를 구분한다. AMD 예제의 switch 9216이나 perftest의 4096을 서로 모순이라고 보거나 하나의 전역 MTU 값으로 복사하지 않는다.[6][7]
  • PFC-free 설계는 검증된 endpoint transport와 switch mode가 있을 때만 채택한다. RF-72513의 Pollara NIC spraying(PFC off)과 switch spraying(PFC on)은 서로 다른 profile이다.[8]

Cumulus Linux 5.14 한정 예시

다음은 일반 lossless RoCE QoS 예제이지 전체 Spectrum-X 배포 명령 세트가 아니다. 기존 lossy 설정에서 단순 nv set qos roce만 실행하면 mode가 전환되지 않을 수 있어 mode를 명시한다.[3]

swp1은 예시이므로 실제 port로 바꾼다. DSCP mapping, PFC pause duration, ECN marked packets, CNP, buffer discard를 검사한다. Cumulus 5.14 문서는 Spectrum-4에서 요청 ECN threshold와 하드웨어 반영 값의 반올림 차이가 나타날 수 있음을 설명한다.[3]

원문

3. 호스트·GPU–NIC 경로 검증

AMD는 GPU와 인접한 NIC, 동일 NUMA domain의 CPU affinity, GPU direct/peer-memory driver를 확인하도록 안내한다. 여러 NIC가 있는 호스트에서는 잘못된 ARP 응답/경로 선택에 따른 ARP flux도 점검한다.[6][7]

주의: ACS/IOMMU 설정 변경을 무조건적인 성능 튜닝으로 적용하지 않는다. AMD 가이드도 가상 장치에서는 ACS/AER 활성화가 필요하다고 구분한다. multi-tenant/VM isolation 요구를 먼저 확인하고 OEM의 해당 구성 지침에 따라 처리한다.[7]

진단 예시(NVIDIA 가이드 기준, 실제 HCA/netdev 이름을 대입):[4]

  • RoCE 포트의 link layer가 Ethernet인지, active 상태와 기대 속도인지 확인한다.
  • GPU-direct 경로를 사용한다고 가정하지 말고 host-memory와 GPU-memory 결과를 비교한다. host-memory만 정상이면 GPU–NIC topology, memory registration, peer-memory/DMA-BUF 경로를 조사한다.
  • MPI/NCCL bootstrap에 필요한 TCP 경로와 RoCE data 경로를 따로 검증한다. NCCL_SOCKET_IFNAME만 맞췄다고 RDMA HCA 선택까지 완료된 것은 아니다.[4][7]

4. 단계별 시험과 통과 기준

아래 단계와 합격 판정은 도입 권고다. 수치 기준은 OEM 보증치·검증 BOM·내부 SLA로 사전에 합의하며, 임의의 line-rate 달성률을 제품 보장으로 제시하지 않는다.

  1. 물리/링크: 모든 NIC와 uplink의 속도/FEC/error counter baseline을 저장한다. 의도하지 않은 downshift와 증가하는 uncorrectable error가 없는지 확인한다.
  2. RDMA 연결: RoCE IP로 rping을 수행한다. 일반 ping 성공만으로 RDMA 세션 성공을 판정하지 않는다.[4]
  3. H2H: NIC pair별 ib_write_bw/ib_send_bw, 작은 메시지 지연을 측정하고 모든 rail과 leaf 조합을 확인한다.[4][7]
  4. D2D: 같은 pair에 GPU memory를 추가한다. CUDA는 설치 빌드의 --use_cuda 및 지원 시 DMA-BUF 옵션, ROCm은 ROCm-enabled perftest의 --use_rocm를 사용한다.[4][7]
  5. 동시 경로: 모든 GPU/NIC를 동시에 사용한다. 단일 NIC 합격 뒤에 PCIe 공유·uplink 병목이 드러날 수 있으므로 단독/동시 결과를 나란히 기록한다.
  6. 장시간 부하: AMD 가이드는 H2H/D2D 다중 NIC 시험을 최소 8시간 유지하는 검증 단계를 제시한다. 현장 정책에서는 냉각·전력·일시적 오류 관측 창과 함께 계획한다.[7]
  7. Collective: NCCL/RCCL 테스트로 correctness와 메시지 크기별 latency·algbw·busbw를 저장한다. AllReduce 외 AllGather/ReduceScatter/AlltoAll 및 cross-rail 배치를 포함한다.
  8. 실제 workload: step-time/처리량·tail·communication overlap과 여러 동시 job의 간섭을 비교한다. microbenchmark가 정상이더라도 이 단계를 생략하지 않는다.

실험 결과에는 node/GPU 수, placement, 단/양방향, 메시지 크기, QP 수, iteration, warm-up, 알고리즘, container digest를 남긴다. busbw를 물리 Ethernet port 전송률로 직접 해석하지 않는다.

GID와 환경 변수 오복사 방지

NVIDIA NCCL 2.21 이상에서는 GID 동적 선택이 도입되어 NCCL_IB_GID_INDEX를 설정하지 않도록 문서화되어 있다. AMD 멀티노드 문서에는 GID 3 예제가 있으나 실제 GID table과 설치 RCCL 버전을 확인해야 한다. NCCL_*라는 동일 이름만으로 두 라이브러리의 동작·기본값이 같다고 단정하지 않는다.[4][7]

AMD RCCL의 multi-node 테스트는 RDMA device를 NCCL_IB_HCA에 나열한다. bnxt_re*와 mlx5_* 등의 예시 이름은 실제 장치 발견 결과로 교체한다. 알고리즘·QP·GDR level 강제는 자동 선택 baseline을 확보한 뒤 한 항목씩 A/B 검증한다.[7]

5. 실패 모드와 장애 시험

다음은 관측 신호를 출발점으로 삼는 진단 가설이며 단일 counter만으로 원인을 확정하지 않는다.

  • ECN/CNP 증가 + 안정적 처리량: 제어 루프가 정상 동작하는 상황일 수 있다. ECN=0만을 목표로 threshold를 높이지 않는다.
  • 긴 PFC pause + tail 증가: 지속 혼잡, 잘못된 QoS mapping, HOL blocking, downstream 정체 가능성. queue/drop·송신률을 동시에 본다.
  • PFC-free 모드의 retry/손실: 손실 0이라는 lossless 기준 대신, 해당 transport의 복구 동작과 tail/SLA 기준을 적용한다.
  • H2H 정상·D2D 저하: GPU–NIC locality, PCIe/NUMA, peer-memory 지원, memory registration 문제를 먼저 분리한다.
  • 단일 rail 정상·전체 rail 저하: uplink oversubscription, 경로 편중, PCIe shared resource 또는 rank/HCA 선택을 점검한다.
  • 시작 단계 hang: bootstrap TCP와 RDMA를 분리하고, 사용할 수 없는 UP 인터페이스, GID, memlock, rank별 설정 불일치를 점검한다.[4]

승인된 유지보수 창에서 leaf–spine 링크, endpoint 링크, plane 장애를 서로 다른 시험으로 수행한다. job 생존 여부, retry/timeout, 정상 대비 throughput, 재수렴 시간과 복구 후 성능을 저장한다. endpoint 단절에도 ECMP만으로 작업이 생존한다고 가정하지 않는다.

6. 인수 산출물

  • BOM/버전 및 topology·rank–GPU–NIC mapping.
  • QoS 계약과 switch/NIC applied·operational 설정 snapshot.
  • H2H/D2D·동시 NIC·collective·실제 workload 결과 및 실패 재현 로그.
  • 오류·ECN/CNP·PFC/queue·GPU 지표를 같은 시간축으로 수집한 자료.
  • 장애 주입/rollback 결과와 알려진 제한, 운영 지원 책임자.

완료 판정: 링크 up이나 AllReduce 단일 성공이 아니라, 합의한 정상·혼잡·장애 조건의 correctness와 SLA를 충족해야 한다. 이 문서 추가 시점에는 실제 NIC/switch 구성이나 GPU 벤치마크를 실행하지 않았다.
