GPU 통신 튜닝: NCCL·RCCL 설정을 안전하게 바꾸는 법

범위와 읽는 법

여러 GPU가 계산 결과를 주고받는 시간을 줄이는 설정이다. GPU를 바쁘게 만드는 것보다 전체 작업을 빨리 끝내는 것이 목표다. 시작 문서는 gpu-cluster-tuning-guide, 네트워크 장비 설정은 gpu-system-tuning이다.

  • A: RTX 6000 Ada. B: RTX PRO 6000 Blackwell Server Edition. M: AMD Instinct MI355X.
  • 확인한 공식 문서: NCCL 2.32.3, RCCL 2.30.4, 접근일 2026-09-30. URL은 갱신되므로 본문 원문을 보존했다. 검색 결과의 오래된 버전명 대신 직접 읽은 문서 제목을 사용했다.[1][2]
  • 공식 기본값은 해당 문서의 값이다. 시작점·시험값은 작성자의 제안이며 GPU별 실측 최적값이 아니다. RCCL 문서에 없는 값은 NCCL에서 복사하지 않는다.
  • 미설정은 변수를 아예 지정하지 않는다는 뜻이다. 문자열 auto나 숫자 0을 대신 입력하는 뜻이 아니다.
  • RDMA는 CPU 메모리를 여러 번 거치지 않고 데이터를 옮기는 통신 방식, HCA는 RDMA 네트워크 장치, QP는 RDMA 통신에 사용하는 송수신 큐 한 쌍이다. CTA는 통신 커널이 GPU에서 사용하는 실행 블록이다.

먼저 지켜야 할 원칙

NCCL은 디버깅 절의 설정을 일반 운영에 계속 남기지 말라고 경고한다. 아래 고급 설정은 문제 재현·짧은 비교 시험용으로 취급한다. NIC 선택 같은 시스템 설정과 알고리즘 강제·통신 비활성화 같은 진단 설정을 구분한다.[1]

C01. NCCL_SOCKET_IFNAME — IP 인터페이스 선택

  • 뜻·적용: 통신에 사용할 IP 인터페이스를 고른다. 초기 연결과 socket 경로 문제를 확인할 때 사용한다.[1][2]
  • 기본값·범위: NCCL은 미설정 시 자동 선택. RCCL도 우선 미설정 기준선을 쓴다. 인터페이스 이름/접두사 목록, ^ 제외, = 정확히 일치 문법을 지원한다. RCCL 표는 숫자 기본값을 제시하지 않는다.[1][2]
  • 조정·부작용: 실제 backend 또는 초기 연결망만 선택한다. 잘못 고르면 연결이 끊기며, 이 변수만으로 RDMA 장치 선택까지 완료되지는 않는다.
  • 확인 지표: 초기 연결 성공, 실제 선택된 인터페이스 로그, socket fallback 여부.
  • GPU별 시작점: A/B/M 모두 미설정으로 경로 확인 → 잘못 선택될 때만 실제 장치명을 지정. eth0를 공통 정답으로 쓰지 않는다.

C02. NCCL_IB_HCA — RDMA 장치 선택

  • 뜻·적용: GPU와 가까운 RDMA 장치를 선택한다. NIC가 여러 개일 때 특히 중요하다.[1][2]
  • 기본값·범위: 수동 필터 미설정에서 시작. 장치[:포트] 목록과 ^/= 문법을 확인한다. NCCL 최신 문서의 추가 rail/plane 문법을 RCCL에 그대로 사용하지 않는다.[1][2]
  • 조정·부작용: GPU–NIC 매핑에 맞춰 정확한 이름을 지정한다. 일부 NIC를 빠뜨리면 대역폭이 줄고, 노드별 장치 수가 다르면 초기화 문제가 생길 수 있다.
  • 확인 지표: GPU별 NIC 선택, NIC별 송수신량, 단독/동시 RDMA 대역폭.
  • GPU별 시작점: A/B는 OEM PCIe 배선에 맞춤. M도 실제 GPU–NIC 매핑에 맞춤. GPU 종류만으로 NIC 이름·개수를 결정하지 않는다.

C03. NCCL_IB_GID_INDEX — RoCE 주소 선택

  • 뜻·적용: 사용할 RoCE 주소 항목을 정한다. 잘못된 주소 계열·VLAN 선택을 진단할 때 확인한다.[2][6]
  • 기본값·범위: NCCL 최신 문서는 2.32u1부터 기본 AUTO, -1은 이전 방식의 별칭이라고 설명한다. RCCL 2.30.4 표는 기본 -1이다. 실제 번호는 현장 GID table 기준이며, 우선 변수를 미설정해 자동 선택을 확인한다. 이름이 같아도 기본 표기를 복사하지 않는다.[1][2]
  • 조정·부작용: 자동 선택으로 연결 가능한지 먼저 확인한다. 예제의 3을 고정하면 다른 서버·VLAN에서 실패할 수 있다.
  • 확인 지표: 실제 선택 주소, RDMA 연결, IPv4/IPv6·VLAN 일치.
  • GPU별 시작점: A/B/M 모두 수동 override 없이 시작. 자동 선택이 틀린 증거가 있을 때만 해당 라이브러리 버전 지침 적용.

C04. NCCL_CROSS_NIC — 서로 다른 NIC 경로 사용

  • 뜻·적용: 같은 통신 그룹에서 노드마다 다른 NIC를 사용하도록 허용할지 정한다. 다중 NIC 네트워크용이다.[1]
  • 기본값·범위: NCCL 기본 2; 0은 같은 NIC 우선 제약, 1은 다른 NIC 허용, 2는 같은 NIC를 선호하되 유리하면 다른 NIC도 허용. NIC 하나면 효과가 없다.[1]
  • 조정·부작용: rail 사이 연결이 느린 경우 0과 비교할 수 있다. 모든 NIC가 같은 스위치로 연결되면 판단이 달라진다. GPU 배치가 비대칭이면 0도 모든 cross-rail 통신을 없애지 못한다.
  • 확인 지표: rail별 사용량, cross-rail 지연, 실제 작업 시간.
  • GPU별 시작점: A/B는 2 유지. M은 이 RCCL 원문만으로 지원·기본값을 확인하지 못했으므로 적용 보류. NCCL 값을 복사하지 않는다.

C05. NCCL_IB_QPS_PER_CONNECTION — 연결당 통신 큐 수

  • 뜻·적용: 여러 경로에 트래픽을 나누기 위한 QP 수다. 여러 단계 스위치에서 경로 편중이 확인된 경우 시험한다.[1]
  • 기본값·범위: NCCL 기본 1, 허용 1–128. network plugin에 따라 실제 적용 경로가 다를 수 있다.[1]
  • 조정·부작용: 제안 시험은 1 → 2 → 4처럼 작은 범위부터. 크게 잡으면 큐 관리 비용과 지연이 늘 수 있으므로 범위 상한을 목표로 삼지 않는다.
  • 확인 지표: 링크별 사용량, 큰 메시지 대역폭, 작은 메시지 지연, 학습/추론 지연.
  • GPU별 시작점: A/B는 기본 1. M은 설치 RCCL 및 NIC plugin 문서에서 지원·기본값을 확보한 뒤 시험하며, 이 표의 NCCL 범위를 적용하지 않는다.

C06. NCCL_IB_SPLIT_DATA_ON_QPS — 여러 QP 사용 방식

  • 뜻·적용: C05에서 QP가 여러 개일 때 메시지를 나눠 보낼지, 메시지마다 QP를 번갈아 쓸지 정한다.[1]
  • 기본값·범위: NCCL 0/1; 2.20 이상 기본 0(번갈아 사용), 2.18–2.19 기본 1(메시지 분할).[1]
  • 조정·부작용: 1은 한 메시지에 여러 QP를 쓰지만 작은 메시지 지연이 나빠질 수 있다. 먼저 QP 수를 정하고 두 모드를 비교한다.
  • 확인 지표: 메시지 크기별 지연·대역폭, 실제 통신 대기 시간.
  • GPU별 시작점: A/B는 해당 버전 기본 유지. M은 별도 검증; C05와 마찬가지로 NVIDIA 기본값을 복사하지 않는다.

C07. NCCL_ALGO — 집단 통신 알고리즘

  • 뜻·적용: 여러 GPU의 결과를 합치거나 나누는 방법을 선택한다. 자동 선택이 특정 메시지에서 느릴 때 진단한다.[1][2]
  • 기본값·범위: NCCL 미설정=자동. Ring/Tree 등 버전·장비가 지원하는 알고리즘만 유효하다. RCCL 문서는 override 기능을 설명하지만 동일한 전체 허용 목록을 보장하지 않는다.[1][2]
  • 조정·부작용: 지원 확인 후 특정 collective만 비교한다. Ring을 제외했는데 대체 알고리즘이 없으면 실패할 수 있다. NVLS는 NVIDIA 전용 기능이므로 AMD나 일반 PCIe 서버의 공통값이 아니다.
  • 확인 지표: AllReduce뿐 아니라 AllGather/ReduceScatter/AlltoAll, 실제 step time.
  • GPU별 시작점: A/B/M 모두 미설정. 플랫폼·작업별 재현 결과가 없으면 강제하지 않는다.

C08. NCCL_PROTO — 통신 프로토콜 강제

  • 뜻·적용: 낮은 지연/높은 대역폭을 위한 내부 전송 방식을 제한한다. 일반 성능 튜닝보다 문제 진단에 한정한다.[1]
  • 기본값·범위: NCCL은 지원되는 프로토콜 자동 사용. 문서의 후보는 LL, LL128, Simple. RCCL 허용 조합은 별도 확인해야 한다.[1][2]
  • 조정·부작용: NVIDIA는 이 변수 설정을 권장하지 않으며, 지원하지 않는 플랫폼에서 LL128을 강제하면 데이터 손상 가능성을 경고한다. 속도만 보고 채택하지 않는다.[1]
  • 확인 지표: 결과 정확성, hang/error, 메시지별 지연과 실제 작업 시간.
  • GPU별 시작점: A/B/M 모두 미설정. 지원 검증 없는 LL128 강제는 금지한다.

C09. NCCL_MIN_CTAS / NCCL_MAX_CTAS — 통신에 줄 GPU 자원

  • 뜻·적용: 통신 커널의 실행 블록 수를 제한한다. 통신 처리량과 모델 계산이 서로 GPU 자원을 빼앗는지 확인할 때 쓴다.[1][2]
  • 기본값·범위: NCCL 미설정, 2.25 이상 1–64(그 이전 상한 32). RCCL 표는 미설정, 양의 정수이며 0 이하 무시로 설명하고 이 표에 같은 상한은 명시하지 않는다.[1][2]
  • 조정·부작용: 수를 늘리면 통신 시험만 빨라지고 모델 계산은 느려질 수 있다. 이전 NCCL_MIN/MAX_NCHANNELS와 중복 강제하지 않는다.
  • 확인 지표: 통신 단독 성능과 실제 작업 성능을 함께 비교; 계산·통신 겹침, GPU 실행 시간.
  • GPU별 시작점: A/B/M 모두 미설정. GPU 크기가 크다는 이유로 최대값을 강제하지 않는다.

C10. NCCL_NET_GDR_LEVEL — GPU와 NIC 직접 전송 범위

  • 뜻·적용: GPU와 NIC가 얼마나 멀리 연결되어 있어도 직접 전송을 쓸지 정한다.[1]
  • 기본값·범위: NCCL 미설정=자동, LOC/PIX/PXB/PHB/SYS 경로 이름. 각각 사용 안 함/같은 PCIe switch/여러 switch/같은 NUMA/NUMA 간 범위다. 구형 숫자 표기는 피한다.[1]
  • 조정·부작용: SYS가 항상 빠르지 않다. 실제 지원 경로·PCIe 병목을 확인하고 직접 전송이 불가능한 구성을 강제로 해결하려 하지 않는다.
  • 확인 지표: host-memory 대비 GPU-memory RDMA, CPU 사용량, NUMA 간 트래픽.
  • GPU별 시작점: A/B는 자동 및 GPU–NIC 경로 실측. M은 AMD direct RDMA 지침과 설치 RCCL 지원을 확인하고 NVIDIA 경로값을 그대로 적용하지 않는다.[6]

C11. RCCL_IB_SPLIT_DATA_THRESHOLD — AMD 메시지 분할 시작 크기

  • 뜻·적용: 여러 NIC/QP로 나눠 보낼 최소 메시지 크기. 해당 다중 경로 기능이 켜져 있을 때 의미가 있다.[2]
  • 기본값·범위: RCCL 2.30.4 문서 기본 128 bytes, 정수 byte 값. 공식 표는 최소·최대 수치 범위를 명시하지 않는다.[2]
  • 조정·부작용: 높이면 작은 메시지 분할 비용을 줄일 수 있지만 여러 경로를 쓸 기회가 줄어든다. 분할 기능의 활성 여부를 먼저 확인한다.
  • 확인 지표: 경계 전후 메시지 지연, NIC별 사용량, AlltoAll 지연.
  • GPU별 시작점: A/B 해당 없음. M은 해당 버전 기본 유지; 다른 RCCL 버전에는 숫자를 이식하지 않는다.

C12. NCCL_P2P_DISABLE / NCCL_IB_DISABLE — 경로 차단 진단

  • 뜻·적용: GPU 직접 통신 또는 IB/RoCE를 끄고 원인 경로를 좁히는 설정이다.[1]
  • 기본값·범위: 정상 경로 사용을 막는 override 없이 시작. NCCL은 1로 해당 전송을 비활성화한다. RCCL 상세 동작은 설치 버전 확인.[1]
  • 조정·부작용: 문제 원인은 분리할 수 있지만 CPU 메모리/socket 우회로 성능이 떨어질 수 있다. 해결 후 반드시 제거한다.
  • 확인 지표: 오류 재현 여부, transport 로그, 처리량 손실, 결과 정확성.
  • GPU별 시작점: A/B/M 모두 진단 때만. 장애 회피값을 운영 최적값으로 저장하지 않는다.

GPU별 우선순위와 실패 방지

권고: A/B는 실제 PCIe GPU–NIC 배치, M은 Infinity Fabric 연결과 노드 간 NIC 배치를 먼저 확인한다. 그 다음 C01/C02로 잘못된 경로를 고치고, 알고리즘 강제는 마지막에 검토한다. M의 XGMI가 정상인지 확인하지 않은 채 네트워크 변수만 바꾸지 않는다.

검증 순서: 작은 입력의 정답 확인 → 단일 GPU/노드 → 노드 간 → 대표 메시지 크기 → 실제 작업. busbw는 시험 도구가 계산한 통신 지표이며 NIC 물리 속도와 바로 비교하지 않는다. timeout·retry 확대는 성능 튜닝이 아니라 장애 감지 지연을 바꾸는 조치로 따로 관리한다.
