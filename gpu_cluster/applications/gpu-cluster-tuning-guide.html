GPU 클러스터 통합 튜닝 가이드

이 문서는 무엇을 도와주나

같은 장비에서 작업을 더 빨리, 더 안정적으로 끝내기 위해 어떤 설정을 어떤 순서로 바꿀지 안내한다. 학습·추론 프로그램, GPU 간 통신, CPU·네트워크·전력 설정을 하나의 절차로 연결했다. 어려운 말은 처음 나올 때 뜻을 함께 적었다.

대상은 RTX 6000 Ada, RTX PRO 6000 Blackwell Server Edition, AMD Instinct MI355X다. 앞의 두 제품은 이름이 비슷하지만 메모리·PCIe·서버 구성·분할 지원이 다르다. 제품명에 6000이 있다는 이유로 같은 설정을 쓰면 안 된다.[7][8]

확인일: 2026-09-30. 이 문서는 공식 문서 조사와 설계 분석 결과다. 실제 GPU 클러스터에서 성능 시험을 수행한 결과가 아니다. GPU 모델만으로 최적값을 정할 수 없으므로 공식 기본값, 권장 시작점, 비교 시험 후보, 미확정 값을 구분한다.

1. 길잡이 — 필요한 부분부터 읽기

  • 학습이 느리거나 메모리가 부족함: gpu-training-tuning — 배치·병렬화·정밀도·DDP·데이터 입력.
  • GPU가 데이터를 기다리거나 준비 시간이 김: gpu-input-compiler-tuning — DataLoader·CPU thread·torch.compile.
  • LLM 응답이 늦거나 동시 요청이 밀림: gpu-inference-tuning — vLLM 메모리·문맥 길이·요청 수·토큰 묶음·병렬화.
  • GPU를 늘렸는데 별로 빨라지지 않음: gpu-communication-tuning — NCCL/RCCL 경로·알고리즘·통신 자원.
  • 입력 대기·RoCE 문제·전력/열 제한이 보임: gpu-system-tuning — CPU 배치·MTU·혼잡 제어·전력·분할·스토리지.

각 설정에는 뜻·적용 조건 → 기본값·허용 범위 → 조정 방향·부작용 → 확인할 지표 → GPU별 시작점이 있다. 값이 장비마다 다르면 “장치 조회값”, 공식 문서에 없으면 “미명시”로 남겼다. 숫자를 채우기 위해 추정하지 않았다.

자주 나오는 용어

  • 처리량: 정해진 시간에 끝낸 작업량. 학습의 samples/s, 추론의 output tokens/s 등이 있다.
  • 지연: 한 작업이나 요청을 끝내는 데 걸린 시간. 처리량이 높아도 개별 요청은 느릴 수 있다.
  • p95/p99: 요청 대부분은 빨라도 일부가 아주 느린지 보는 지표. 각각 95%/99% 요청이 그 시간 이내에 끝나는 경계다.
  • SLO: 서비스가 지키기로 한 응답 속도·오류율 목표. 여기서는 “응답 목표”라고도 부른다.
  • OOM: GPU나 CPU 메모리가 모자라 작업이 실패하는 상황.
  • baseline: 아무 값이나 강제하기 전, 정상 지원 구성에서 측정한 기준 성능.
  • rank: 분산 작업에 참여하는 프로세스의 번호. “GPU 번호”와 항상 같은 의미는 아니다.
  • collective: 여러 GPU가 함께 데이터를 합치거나 나누는 통신. NCCL은 NVIDIA용, RCCL은 AMD용 라이브러리다.[1][2]

2. 먼저 정할 목표

작성자 권고: 목표 하나와 지켜야 할 제한을 먼저 고른다.

  • 학습: 같은 모델·데이터·학습 품질에서 step time(한 번의 학습 반복 시간)을 줄인다. 최종적으로 목표 품질까지 걸리는 시간을 본다.
  • 대화형 추론: 첫 응답 시간(TTFT), 이후 토큰 간 지연(ITL/TPOT), p95/p99 응답 목표를 지키는 처리량을 높인다. TPOT는 보통 요청별 평균 생성 간격, ITL은 실제 토큰 사이 간격이므로 도구의 정의를 기록한다.
  • 일괄 추론: 요청 마감 시간을 지키면서 전체 완료 시간·비용을 줄인다.
  • 전력 효율: 동일 품질·지연 조건에서 작업당 에너지를 줄인다. GPU만 측정했는지 서버 전체를 측정했는지 구분한다.

GPU 사용률 100%, 최대 batch, 최대 tokens/s 하나만을 성공 기준으로 쓰지 않는다. queue에서 오래 기다리게 해도 처리량은 높아 보일 수 있다. 학습에서는 배치를 바꾸면 최적화 과정 자체가 달라질 수 있다.

3. 시작 전 기록 — 나중에 같은 결과를 다시 만들기 위해

다음을 한 묶음으로 저장한다. 실제 설정에 맞는 버전 문서를 사용한다.

  1. 정확한 GPU 제품/edition, GPU 수, OEM 서버, CPU/RAM, NIC와 switch, 전력 cap·partition.
  2. OS/kernel, GPU driver, CUDA 또는 ROCm, PyTorch/vLLM, NCCL/RCCL, NIC firmware·plugin, 컨테이너 digest.
  3. GPU–CPU–NIC 연결도, GPU와 rank 배치, 노드 수, CPU/메모리 제한.
  4. 모델 revision·정밀도·양자화 방식, 입력/출력 길이 분포, 학습 데이터, 글로벌 배치 또는 요청 도착 패턴.
  5. 명령행 인수, 환경 변수, 설정 파일. 지정한 값과 실행 시 실제 적용된 값을 구분한다.
  6. 정상 기준 성능, 오류 로그, 온도/전력, 측정 구간, 원복할 설정 백업.

latest URL은 현재 바뀌는 문서다. 이번 조사에서는 NCCL 2.32.3/RCCL 2.30.4 문서를 읽었지만, 이를 설치 권장 버전으로 지정한 것은 아니다.[1][2] 라이브러리가 framework/container 안에 들어 있으면 host 패키지 버전만 기록하지 않는다.

4. 병목에 따라 조정 순서를 선택

아래는 관측 신호에서 시작하는 진단 가설이다. 하나의 지표만으로 원인을 확정하지 않는다.

  • GPU가 자주 쉬고 입력 대기가 큼: 저장장치·DataLoader worker/prefetch → CPU thread·NUMA → host-to-device 전송 확인. 통신 알고리즘부터 바꾸지 않는다.
  • 메모리가 모자람: 필요한 입력/문맥 길이 확인 → microbatch/동시 요청 감소 → 정밀도·재계산·모델 분할 검토. 정확도나 기능을 줄였으면 별도 비교군으로 표시한다.
  • 단일 GPU는 정상, 여러 GPU에서 느림: GPU pair 연결 → NIC 선택·RDMA → 실제 메시지별 collective → TP/PP/DP 배치 → 고급 통신 변수 순서.
  • 추론 첫 응답만 느림: queue 대기와 입력 처리(prefill)를 분리 → token budget·chunked prefill·prefix cache 확인.
  • 생성 도중 끊기거나 일부 요청이 매우 느림: 동시 요청·decode 경쟁 → 긴 prefill 간섭 → KV cache 부족/재계산 → 네트워크·열 제한 확인.
  • 처음에는 빠르다가 느려짐: 온도·clock 제한 → 전력 cap → 메모리/cache 상태 → I/O 동시 부하 확인.

순서는 bottleneck-analysis의 “측정 → 원인 분리 → 한 가지 변경 → 재측정” 원칙과 연결된다.

5. GPU별 권장 시작점 — 최적값이 아니라 첫 비교 기준

RTX 6000 Ada

  • 공식 제품 사양은 48GB GDDR6, PCIe Gen4, 최대 300W다. Blackwell 서버용 기능·BOM을 적용하지 않는다.[7]
  • 권고: 모델과 작업 메모리가 한 GPU에 들어가면 TP=1의 독립 추론 인스턴스부터 측정한다. 메모리가 모자랄 때만 정확도 검증을 전제로 양자화·분할을 비교한다.
  • 학습은 작은 microbatch에서 시작해 여유를 확인한다. 통신 경로는 OEM PCIe 배선과 실제 GPU pair 시험으로 확인한다.
  • NCCL 알고리즘/프로토콜은 자동. power cap은 현재 OEM 허용값 유지. MIG를 Blackwell에서 복사하지 않는다.

RTX PRO 6000 Blackwell Server Edition

  • 공식 제품은 96GB GDDR7, PCIe Gen5, 최대 600W configurable, 최대 4 MIG instance를 설명한다. profile 지원은 배포 조합별 확인 사항이다.[8]
  • 권고: 단일 GPU 적재 가능 모델은 TP=1과 replica 확장을 먼저 비교한다. 큰 모델은 필요한 최소 TP부터 시작하되 실제 응답 목표로 판단한다.
  • Ada보다 메모리가 크다는 이유로 batch/동시 요청을 같은 비율로 늘리지 않는다. PCIe·NIC 공유와 긴 요청의 영향을 별도로 본다.
  • 단일 큰 작업은 partition 없는 기준선, 작은 여러 작업은 MIG 공유 기준선을 별도로 측정한다. 기본 통신 자동 선택을 유지한다.

AMD Instinct MI355X

  • 공식 사양은 288GB HBM3E, 8-GPU Infinity Fabric 연결, 1400W DLC 제품이다. 노드 내부 연결과 노드 외부 Ethernet/RDMA는 다른 경로다.[9]
  • 권고: 단일 GPU에 들어가는 추론은 TP=1부터. 분할이 필요하면 먼저 한 노드의 Infinity Fabric 안에서 필요한 최소 TP를 비교하고, 노드를 넘는 통신은 따로 평가한다.
  • ROCm·RCCL·attention/quantization kernel의 해당 GPU 지원부터 확인한다. 하드웨어가 FP8/낮은 정밀도를 지원해도 현재 모델·커널의 성능/정확도까지 보장하지 않는다.
  • RCCL은 자동 선택 유지. NVIDIA 설정값을 동일한 NCCL_* 이름만 보고 복사하지 않는다.[2]
  • compute/memory partition은 드라이버 지원값을 조회하고 전력·직접 수랭 조건을 우선한다. RA와 최신 문서의 partition 설명 차이는 amd-mi355x-cluster-reference-architecture에 기록되어 있다.[9][10]

6. 비교 시험 — 한 번 빨랐다는 이유로 채택하지 않기

아래는 현장 적용을 위한 제안 절차다. 이 문서 작성 중 실행한 시험이 아니다.

  1. 안전성 확인: 같은 작은 입력으로 정답/학습 loss/오류 여부를 확인한다.
  2. 기준 성능 측정: 기존 설정 A로 준비 실행(warm-up) 후 측정한다. 모델 로딩·컴파일 시간을 본 실행과 구분한다.
  3. 후보 설정 측정: 설정 하나만 바꾼 B를 같은 조건에서 측정한다. QP 수/분할 방식처럼 묶이는 항목은 상호작용을 별도 실험한다.
  4. 되돌려 확인: A → B → A 순서로 환경 변화인지 구분한다. 각 조건은 여러 번 반복하고 중앙값·변동 폭·긴 지연을 함께 남긴다.
  5. 실제 부하로 확대: 작은 시험 → 대표 길이/메시지 크기 → 여러 동시 작업 → 장시간 → 필요 시 승인된 장애/복구 시험.
  6. 채택 여부 결정: 이득이 측정 변동보다 충분히 크고, 정확도·지연·메모리·안정성·다른 사용자 영향의 제한을 모두 지킬 때만 반영한다.

공정한 비교: 추론은 동일한 요청 도착 패턴·길이 분포·cache 상태에서 비교한다. 학습은 가능하면 글로벌 배치를 유지한다. 변수를 바꾼 결과 입력 길이·품질·GPU 수까지 달라졌다면 “같은 조건에서의 성능 개선”으로 보고하지 않는다.

숫자 대신 먼저 사용할 판정식

출력 token/s에 입력 토큰을 섞지 않는다. GPU에 들어오지 못하고 대기·거절된 요청도 함께 보고한다. 물리 NIC 속도, 메모리 대역폭, collective의 busbw를 같은 단위라는 이유만으로 동일 지표로 취급하지 않는다.

실험 기록 양식 — 빈칸을 실제 값으로 채우기

7. 당장 하지 말아야 할 일과 남은 확인 사항

  • LL128 등 프로토콜을 지원 확인 없이 강제하지 않는다. NCCL 공식 문서는 데이터 손상 가능성을 경고한다.[1]
  • PFC/ECN·power cap·partition을 운영 클러스터 전체에서 한 번에 바꾸지 않는다. gpu-system-tuning의 원복 절차를 따른다.
  • ACS/IOMMU/ECC/thermal 보호를 “빠르게 만드는 스위치”로 취급하지 않는다.
  • 미확정: 실제 GPU별 최적 microbatch/TP/동시 요청, 장비별 QoS threshold, power cap별 성능 곡선, storage stripe 값. 실제 모델·버전·OEM·요청 분포와 시험 결과가 있어야 확정할 수 있다.
  • 갱신 조건: GPU/driver/framework/library/NIC firmware가 바뀌면 지원 범위·기본값·실제 적용값을 다시 확인한다. 예전 시험값을 새 버전의 기본값으로 남기지 않는다.
