기반 기능 EPIC E01–E04 핵심 스토리

범위와 표기

VDA 5050 3.0.0은 로봇과 관제가 주고받을 통신을 정해요. 하지만 교통 알고리즘·업무 연결·안전·보안까지 해결하는 완제품은 아니에요.[11] 아래는 그 밖에 무엇을 만들지 정리한 개발 제안이에요. 표준이 반드시 요구하는 항목 목록은 아닙니다.

스토리는 사용자가 원하는 일을 한 가지씩 적은 것이에요. EPIC은 관련 스토리를 모은 큰 기능 묶음이고, 이 문서에는 EPIC마다 10개씩 있어요. 각 항목의 사용자 이야기를 읽고, 바로 아래 수용 기준에서 “무엇을 확인하면 됐다고 볼까?”를 살펴보세요. 사용자 이야기는 이해를 돕기 위한 요구사항 표현이지 실제 인터뷰 인용은 아니에요.

P0는 첫 시험 운영(파일럿) 전에 필요하고 M12 안에, P1은 제품화를 위해 M24 안에 끝내려는 목표예요. P2는 Y3~Y5의 확장 후보예요. M은 착수 후 개월, Y는 연차예요. M6는 6개월째 시작이 아니라 6개월 안에 검증까지 끝내겠다는 뜻이에요. 착수일·용량·허용 오차는 현장과 정해야 해요. 시험 통과가 현장 전체의 무사고·무결함을 보장하지는 않습니다.

공통 완료 기준(DoD)과 개발 작업 묶음은 개발 계획, 지표와 다음 단계의 통과 조건(게이트)은 로드맵에서 확인하세요.

E01 — 자산·현장 모델

먼저 장비 명부와 현장 지도를 맞추는 일이에요. 같은 이름의 로봇을 구분하고, 어디서 무엇을 할 수 있는지 정리해야 배차도 제대로 할 수 있죠.

  • E01-01 · 공장·구역 ID (P0, M6) — 현장 관리자: “이름이 같은 로봇이 다른 공장에도 있어요. 소속을 확실히 구분해서 엉뚱한 공장에 명령하지 않게 해 주세요.”

    • 수용 기준: 다른 공장의 동일 자산명이 있을 때 ID로 구분되고 타 공장 명령은 거부·기록돼요.

  • E01-02 · 로봇 능력 등록 (P0, M6) — 연동 담당자: “이 로봇이 들 수 있는 무게와 크기, 쓸 수 있는 도구를 등록하고 싶어요. 못 하는 일을 배정하면 안 되니까요.”

    • 수용 기준: 능력이 없거나 검증되지 않은 로봇에 조건부 작업을 요청하면 배차 후보에서 제외되고 이유가 남아요.

  • E01-03 · 설비·공유 자원 등록 (P0, M6) — 자동화 담당자: “충전기·통로·물품 인계 지점을 등록해서 예약이 실제 설비와 연결되게 하고 싶어요.”

    • 수용 기준: 존재하지 않거나 사용 중지된 자원을 참조한 임무가 실행 전에 거부돼요.

  • E01-04 · 지도 버전 지정 (P0, M9) — 현장 엔지니어: “관제와 로봇이 서로 다른 지도를 보면 목적지가 달라질 수 있어요. 승인된 같은 지도를 쓰는지 확인하고 싶어요.”

    • 수용 기준: 관제와 로봇의 지도 버전이 맞지 않으면 해당 구역 신규 지시를 보류하고 차이를 표시해요.

  • E01-05 · 좌표계 검증 (P0, M9) — 연동 담당자: “관제의 좌표를 로봇 좌표로 바꿨을 때 같은 장소를 가리키는지 확인하고 싶어요.”

    • 수용 기준: 합의한 기준점과 방향 시험에서 허용 오차를 벗어나면 지도 활성화를 거부해요.

  • E01-06 · 작업 지점 유효성 (P0, M9) — 물류 담당자: “짐을 싣는 곳, 건네는 곳, 기다리는 곳을 구분하고 싶어요. 맞지 않는 설비에 붙도록 지시하면 안 되니까요.”

    • 수용 기준: 용기/로봇과 호환되지 않는 인계점을 지정하면 임무 검증이 실패하고 대안을 안내해요.

  • E01-07 · 정비 상태 관리 (P0, M12) — 정비 담당자: “정비 중인 로봇에는 새 일을 주지 않았으면 해요. 이미 맡은 일이 있다면 정해진 절차로 넘겨야 하고요.”

    • 수용 기준: 정비 전환 시 신규 배차가 차단되고 진행 임무는 합의된 인계 절차로만 처리돼요.

  • E01-08 · 부착물 구성 (P1, M18) — 정비 담당자: “로봇의 도구를 바꾸면 할 수 있는 일도 달라져요. 교체 이력과 확인 결과를 배차에 반영하고 싶어요.”

    • 수용 기준: 부착물 변경 뒤 검증 승인이 없으면 관련 작업 능력이 활성화되지 않아요.

  • E01-09 · 구성 승인·되돌리기 (P1, M21) — 공장 관리자: “설정을 바꾸기 전에 영향을 검토하고 싶어요. 문제가 생기면 이전 설정으로 돌아갈 수도 있어야 해요.”

    • 수용 기준: 새 구성 승인자·영향 임무·버전이 기록되고 되돌리기 후 진행 임무와 충돌 여부를 대조해요.

  • E01-10 · 자산 이력 내보내기 (P1, M24) — 감사 담당자: “장애가 난 시점에 어떤 지도·도구·설비 설정을 썼는지 변경 이력으로 확인하고 싶어요.”

    • 수용 기준: 자산·시간을 지정하면 당시 지도·능력·설비 구성과 승인 근거를 권한 범위 내에서 내보내요.

E02 — 이기종 연동

제조사마다 다른 로봇과 대화하는 부분이에요. 어댑터는 명령과 상태를 맞춰 주는 통역 프로그램이고, SDK는 이를 만들 때 쓰는 개발 도구예요. 여기서 계약은 법률 계약이 아니라 데이터·동작의 약속을 뜻해요. API는 프로그램 사이의 요청 창구, UI는 사람이 조작하는 화면입니다.

  • E02-01 · 어댑터 개발 계약 (P0, M6) — 연동 개발자: “제조사마다 연결 방식이 달라도 관제의 핵심 기능을 매번 고치고 싶지는 않아요. 공통 연결 약속이 필요해요.”

    • 수용 기준: 시험용 모의 장비와 실제 지원 장비를 같은 계약 시험에 넣어 상태·명령·오류 필수 항목을 검사해요.

  • E02-02 · VDA 버전 프로파일 (P0, M9) — 연동 담당자: “장비마다 어느 VDA 버전을 쓰는지 정해 두고 싶어요. 모르는 사이에 다른 버전으로 변환되면 곤란해요.”

    • 수용 기준: 2.x/3.x 대상의 지원 필드·동작·공식 기준 PDF와 메시지 형식(schema) 목록이 고정되고 미지원 버전은 실행 전 거부해요.

  • E02-03 · 공급사 API 연결 (P0, M9) — 통합 담당자: “표준을 쓰지 않는 기존 로봇도 제조사의 API를 통해 연결하고 싶어요.”

    • 수용 기준: 승인된 공급사 API의 명령·상태·권한 시험과 단절 시험이 실제 대상 장비에서 통과해요.

  • E02-04 · 지원 능력 계약 (P0, M9) — 운영자: “이 로봇에서 취소나 일시정지가 어디까지 되는지 알고 싶어요. 안 되는 조작을 누르게 하면 안 되겠죠.”

    • 수용 기준: 미지원 동작은 UI/API 양쪽에서 차단되고 버전별 지원표와 오류 사유가 일치해요.

  • E02-05 · 상태 정규화 (P0, M6) — 관제 운영자: “제조사 원본 상태와 관제가 해석한 상태를 같이 보고 싶어요. 모르는 오류를 정상이라고 보여 주면 안 돼요.”

    • 수용 기준: 관측/수신 시각·순서·원본 오류를 보존하고 오래되거나 미지의 상태를 정상으로 매핑하지 않아요.

  • E02-06 · 응답 단계 구분 (P0, M6) — 백엔드 개발자: “로봇이 명령을 받았다는 것과 실제 일을 끝냈다는 것을 따로 확인하고 싶어요.”

    • 수용 기준: 명령을 받았다는 응답(ACK)만 도착한 시험에서 임무는 완료되지 않고 별도의 완료 증거를 기다려요.

  • E02-07 · 재접속 상태 대조 (P0, M12) — 운영자: “연결이 돌아왔을 때 로봇이 이미 일을 마쳤는지부터 확인하고 싶어요. 같은 물건을 다시 나르면 안 되니까요.”

    • 수용 기준: 완료 직전 단절 후 연결해도 진행/완료 상태를 조회·대조하기 전 같은 물리 작업을 재지시하지 않아요.

  • E02-08 · 불량 메시지 격리 (P0, M12) — 연동 개발자: “장비 하나가 잘못된 메시지를 보내도 나머지 로봇의 관제는 계속됐으면 해요.”

    • 수용 기준: 형식이 틀린 메시지·지나치게 큰 메시지·순서가 뒤집힌 상태를 주입해 격리·진단하고 정상 장비 처리가 지속됨을 확인해요.

  • E02-09 · 공급사 적합성 묶음 (P1, M24) — 구매·QA 담당자: “공급사가 지원한다고 말한 기능을 같은 조건의 시험으로 확인하고 싶어요.”

    • 수용 기준: 공급사·모델·펌웨어·프로파일별 정상/오류/재접속 결과와 미지원 항목을 보고서로 발행해요.

  • E02-10 · 어댑터 호환 업그레이드 (P2, Y3) — 플랫폼 운영자: “연결 프로그램을 업데이트해도 진행 중인 작업의 의미와 기록은 그대로 지키고 싶어요.”

    • 수용 기준: 이전 버전과 후속 버전에서 연결 약속이 유지되는지 다시 시험해요. 실패 시 되돌리기도 시험하고, 진행 중인 임무의 해석이 달라지면 배포를 차단해요.

E03 — 임무·명령 생명주기

작업 한 건을 접수해서 실제로 끝낼 때까지 따라가요. 아래에서는 이 작업을 ‘임무’라고 불러요. 원장은 최종 기준 기록, 상태기계는 가능한 진행 단계와 변경 규칙, outbox는 작업 기록과 함께 저장하는 보낼 메시지 목록이에요. 특히 ‘답을 못 받음’과 ‘일을 안 함’을 같게 보면 안 돼요.

  • E03-01 · 중복 안전 접수 (P0, M6) — 업무 연동자: “응답이 없어서 요청을 다시 보낼 수 있어요. 그래도 운반 작업은 하나로만 만들어 주세요.”

    • 수용 기준: 같은 요청 ID·내용을 반복하면 같은 임무를 반환하고, 같은 ID에 다른 내용이면 충돌을 기록해요.

  • E03-02 · 명시적 상태기계 (P0, M6) — 운영자: “일이 어느 단계에서 멈췄는지 알고 싶어요. 상태를 알아야 맞는 조치를 할 수 있으니까요.”

    • 수용 기준: 허용되지 않은 진행 단계 변경을 거부하고 상태불명·보류·취소요청을 완료와 구분해요.

  • E03-03 · 명령 저널·outbox (P0, M6) — 백엔드 담당자: “명령을 보내기 전후에 서버가 꺼져도 어떤 지시가 사라졌는지 기록으로 확인하고 싶어요.”

    • 수용 기준: 기록을 저장하고 명령을 보내는 사이에서 프로세스를 종료해도 승인된 요청의 기록과 재전송 대상이 식별돼요.

  • E03-04 · 물리 인계 완료 (P0, M9) — 물류 담당자: “로봇이 도착한 것만으로 끝내지 말고, 맞는 물품을 실제로 건넸는지 확인하고 싶어요.”

    • 수용 기준: 로봇 도착만 있고 스캔/설비 수락이 없으면 임무는 완료되지 않고 인계 확인 대기로 남아요.

  • E03-05 · 취소 수명주기 (P0, M9) — 운영자: “취소 요청이 처리 중인지, 정말 취소됐는지 알고 싶어요. 로봇에 실린 물품을 방치하면 안 되니까요.”

    • 수용 기준: 취소 응답 유실·거부·적재 중 상황을 각각 시험하고 현장 대조 없이 취소완료로 바뀌지 않아요.

  • E03-06 · 보류·재개 계약 (P1, M15) — 운영자: “멈췄던 작업은 필요한 확인과 승인을 거친 뒤에만 다시 시작하고 싶어요.”

    • 수용 기준: 보류 원인이 해소돼도 권한·점유·장비 상태 검증과 필요한 승인 전에는 신규 실행 명령이 나가지 않아요.

  • E03-07 · 적재 작업 재할당 (P1, M18) — 물류 운영자: “짐을 실은 로봇이 고장 나면 물품을 먼저 확인하고 다른 로봇으로 옮기고 싶어요.”

    • 수용 기준: 물품을 회수하거나 건넸다는 증거 없이 적재 중인 작업을 다른 로봇에 자동 배정하지 않아요. 새 작업과 원래 작업의 연결도 남겨요.

  • E03-08 · 다단계 임무 보상 (P1, M18) — 업무 설계자: “뒤 단계가 실패했다고 이미 내려놓은 물건까지 원래대로 돌아간 것은 아니에요. 실제 인계 기록은 남겨 주세요.”

    • 수용 기준: 하역 완료 후 후속 단계 실패 시 물리 완료 이력을 유지하고 승인된 회수·대체 단계만 생성해요.

  • E03-09 · 재시작 대조 큐 (P0, M12) — 운영자: “서버를 다시 켰을 때 상태를 모르는 작업부터 찾아 현장과 맞춰 보고 복구하고 싶어요.”

    • 수용 기준: 서버를 다시 켰을 때 기준 기록·로봇·설비의 상태가 서로 다른 작업은 확인 목록에 넣어요. 확인 없이 자동 완료 처리하거나 공간을 비었다고 바꾸지 않아요.

  • E03-10 · 업무 통지 재전송 (P0, M12) — MES/WMS 담당자: “완료 통지의 응답이 사라져도 생산·재고 기록을 맞출 수 있게 다시 알려 주세요.”

    • 수용 기준: 완료 통지를 반복해도 업무 실적은 중복 반영되지 않으며 미수락 통지가 목록과 알람에 남아요.

E04 — 배차·생산 우선순위

누구에게 어떤 일을 먼저 맡길지 정하는 부분이에요. 대기 노화는 오래 기다린 정도를 반영하는 방식이고, 기아는 특정 작업이 계속 밀려 처리되지 못하는 상태예요. Trace는 작업 종류와 들어온 순서를 기록한 자료예요. Shadow 시험에서는 같은 자료로 새 계획을 계산하되 실제 로봇에는 명령하지 않아요.

  • E04-01 · 능력·상태 필터 (P0, M9) — 생산기술 담당자: “조건에 맞는 로봇만 골라야 해요. 현장에 가서야 못 하는 일임을 알게 되는 상황을 줄이고 싶어요.”

    • 수용 기준: 중량·도구·지도·정비·통신 조건이 부적합한 후보가 제거되고 제거 근거가 저장돼요.

  • E04-02 · 마감 기반 우선순위 (P0, M9) — 물류 담당자: “마감이 가까운 일도 중요하지만 오래 기다린 일도 계속 밀리면 안 돼요. 둘 다 보고 배차하고 싶어요.”

    • 수용 기준: 마감·긴급도·노화가 다른 고정 trace에서 승인된 규칙대로 선택되고 선택 사유가 재현돼요.

  • E04-03 · 단순 배차 기준선 (P0, M9) — QA 담당자: “새 배차 방식이 정말 나아졌는지 비교할 수 있도록 반복 시험이 가능한 기본 방식을 두고 싶어요.”

    • 수용 기준: 동일 입력/버전/조건에서 기준 정책의 배차 기록이 재현되고 정책 설정이 보고서에 포함돼요.

  • E04-04 · 생산 순서 변경 (P1, M18) — 라인 담당자: “생산 순서가 바뀌면 운반도 조정하고 싶어요. 다만 이미 실린 물품은 계속 추적해야 해요.”

    • 수용 기준: 적재 전/후 순서 변경을 구분해 보류·우회·재할당 여부를 결정하고 기존 물품 추적을 잃지 않아요.

  • E04-05 · 충전 계획 (P1, M18) — 운영자: “충전 대기까지 보고 배차해서 일하는 도중 배터리가 부족해지는 일을 막고 싶어요.”

    • 수용 기준: 공급사가 승인한 배터리 조건과 예약 충전기를 만족하지 못하면 새 임무를 배정하지 않고 이유를 표시해요.

  • E04-06 · 대체 목적지 선택 (P1, M18) — 물류 담당자: “원래 인계 지점을 쓸 수 없으면 미리 승인된 대기 장소를 이용하고 싶어요.”

    • 수용 기준: 불능 목적지 임무는 호환 능력·용량·승인을 확인한 대안만 선택하고 원래 업무 요청과 연결돼요.

  • E04-07 · 기아 탐지 (P1, M18) — 운영자: “급한 일이 계속 들어와도 오래 밀린 주문을 찾아 챙기고 싶어요.”

    • 수용 기준: 우선순위 높은 작업을 반복 주입하면 합의된 대기 기준 초과 임무가 탐지되고 조치 이력이 남아요.

  • E04-08 · 수동 우선순위 조정 (P1, M18) — 생산 책임자: “긴급 요청의 우선순위를 바꾸되 다른 작업에 어떤 영향이 있는지 확인하고 싶어요.”

    • 수용 기준: 변경 사유·권한·영향받는 임무·승인이 기록되고 안전/능력 제약은 우선순위로 우회되지 않아요.

  • E04-09 · Shadow 정책 비교 (P2, Y4) — 제품 책임자: “새 배차 정책이 더 나은지 실제 명령은 보내지 않은 채 먼저 비교하고 싶어요.”

    • 수용 기준: 동일 trace에서 기준/후보의 납기·최장대기·개입 지표를 비교하고 후보가 실제 명령을 보내지 않음을 검증해요.

  • E04-10 · 제한적 최적화 배포 (P2, Y4) — 운영 책임자: “효과가 확인된 정책만 제한된 범위에 적용하고, 나빠지면 기존 방식으로 돌아가고 싶어요.”

    • 수용 기준: 허용 구역·평가기간·악화 기준을 사전 승인하고 기준 초과 시 기존 정책으로 복귀·임무 대조해요.

의존성·한계와 연결

아직 확정 명세가 아니라 검토할 초안이에요. 공급사가 실제로 지원하는 기능, 명령 권한, 현장 위험 평가를 보고 구현을 나누거나 범위를 조정해야 해요. P0를 만들지 않은 채 생산 적용을 넓혀도 된다고 가정하면 안 돼요. 시험 운영 범위를 바꾸고 다시 승인받아야 합니다. 무엇을 먼저 맞출지는 개발 계획의 EPIC별 선행 조건을 따르세요.
