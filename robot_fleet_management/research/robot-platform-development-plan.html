로봇 관제 플랫폼 개발 목록과 EPIC 분류

개발 전략과 산출물

“관제 플랫폼을 만들자”는 말만으로는 누가 무엇부터 개발해야 할지 알기 어려워요. 그래서 큰 기능 묶음 → 나눠 맡을 개발 작업 → 사용자가 원하는 동작 순서로 정리했어요. 실제 현대자동차의 발주 목록이나 확정 견적은 아니고, 검토를 시작하기 위한 개발 목록인 백로그예요.

여기서 EPIC은 관련 기능을 묶은 큰 개발 단위예요. 예를 들어 ‘임무·명령 관리’가 EPIC이고, ‘같은 요청을 두 번 받아도 운반은 중복으로 시키지 않기’가 그 안의 스토리예요. 스토리마다 무엇을 확인하면 구현됐다고 볼지, 즉 수용 기준도 적었어요.

기술적으로는 Open-RMF의 여러 로봇 집단 관리 범위, VDA 5050이 다루는 통신과 다루지 않는 영역, NIST가 함께 강조하는 현장 설비의 신뢰성·안전을 참고했어요.[10][11][9] 아래 개발 분류·담당·일정은 이 근거를 바탕으로 만든 제안입니다.

전체는 12개 EPIC → 48개 개발 패키지 → 120개 핵심 스토리예요. 패키지는 일을 나눠 맡기 편하게 묶은 단위로, 추가 스토리가 아니에요. EPIC마다 패키지 4개가 스토리 01–03 / 04–06 / 07–08 / 09–10을 나눠 담습니다.

EPIC 분류와 책임

각 팀이 어디까지 맡는지와 먼저 맞춰야 할 약속을 함께 적었어요. ‘먼저 필요하다’는 것은 앞 EPIC 전체가 끝날 때까지 기다리라는 뜻은 아니에요. ID나 메시지 형식 같은 최소 약속을 먼저 맞추고 병행할 수 있습니다. 보안(E09), 안전(E10), 시험(E11)은 처음부터 함께 진행하고, 모든 출시 전에 공통으로 확인해야 해요.

  • E01 자산·현장 모델: 로봇·지도·설비를 같은 이름과 뜻으로 관리해요. 플랫폼의 업무 모델 담당팀이 맡고, 먼저 현장 장비를 조사해요.
  • E02 이기종 연동: 제조사가 달라도 명령과 상태를 연결해요. 로봇 연동팀이 맡고, E01의 장비 ID·능력 표현을 먼저 맞춰요.
  • E03 임무·명령 생명주기: 요청부터 실제 인계까지 작업을 따라가요. 핵심 서버 기능을 만드는 백엔드팀이 맡고, E01/E02의 데이터·통신 약속이 필요해요.
  • E04 배차·생산 우선순위: 마감과 장비 능력을 보고 일을 배정해요. 배차 개발팀과 생산기술 담당자가 함께 맡아요. E03의 작업 상태와 E06의 생산 업무 의미를 알아야 해요.
  • E05 교통·공유 자원: 통로와 설비의 예약·실제 사용·인계를 조정해요. 로봇 제어 연동팀이 맡고, E01 지도와 E02에서 제어할 수 있는 범위를 확인해요.
  • E06 제조업무 통합: 생산·재고·품질 기록과 물품 인계를 맞춰요. 제조 IT팀이 맡고, E01/E03의 데이터와 작업 처리 약속을 먼저 정해요.
  • E07 운영 UX·예외 대응: 운영자가 상태를 이해하고 승인된 복구를 수행할 화면·절차를 만들어요. 제품·화면 개발팀과 현장 운영자가 맡고, E03/E05/E06의 사건 기록을 받아요.
  • E08 엣지·신뢰성·망: 공장 안의 서버가 단절·재시작 뒤에도 권한과 기록을 복구하게 해요. 플랫폼·서비스 안정성 담당(SRE)과 현장 네트워크 담당이 맡아요. E02/E03에서 무엇을 저장할지 먼저 정해야 해요.
  • E09 보안·거버넌스: 허가받은 사람과 장비만 허용된 조작을 하게 해요. 보안·플랫폼팀이 맡고, 공장의 계정·권한 관리(IAM)와 접속 정책을 따라요.
  • E10 안전 검증·운영 통제: 위험·책임·시험 증거와 재개 절차를 관리해요. 안전 책임자와 자동화·운영 담당이 맡고, 기능 개발 전부터 현장 위험을 조사해요.
  • E11 시험·시뮬레이션·출시: 정상 때뿐 아니라 고장 때도 동작을 반복 확인해요. 시험 담당(QA), 플랫폼팀, 공급사가 맡고 최소 통신 약속이 나올 때부터 시험을 붙여요.
  • E12 분석·멀티공장·지능화: 성과와 비용을 확인하고 검증된 구성을 다른 공장에 활용해요. 데이터·제품팀과 공장 운영자가 맡아요. E01/E03/E07의 기록이 먼저 믿을 만해야 해요.

개발 목록 — 패키지와 스토리 매핑

D01 같은 번호는 개발 패키지, E01-01 같은 번호는 스토리예요. 먼저 필요한 묶음을 찾고 연결된 스토리에서 사용자 요구와 확인 방법을 읽으면 됩니다.

기반 기능: robot-platform-stories-foundation

  • D01 / E01-01~03: 공장·구역·장비의 ID를 정하고, 로봇 능력과 설비 정보를 등록해요.
  • D02 / E01-04~06: 지도 버전과 좌표를 맞추고, 출발·인계 지점이 올바른지 확인해요.
  • D03 / E01-07~08: 정비 중인지, 어떤 도구를 장착했는지 관리해요.
  • D04 / E01-09~10: 설정 변경을 승인·되돌리고, 장비의 과거 기록을 꺼내 볼 수 있게 해요.
  • D05 / E02-01~03: 연결용 개발 도구(SDK), VDA 버전별 약속, 제조사 API를 준비해요.
  • D06 / E02-04~06: 지원 동작을 맞추고, 제조사별 상태와 응답을 공통 뜻으로 바꿔요.
  • D07 / E02-07~08: 재접속 뒤 상태를 맞춰 보고, 잘못된 메시지는 따로 처리해요.
  • D08 / E02-09~10: 공급사 지원 주장을 확인할 시험과 버전 변경 시험을 준비해요.
  • D09 / E03-01~03: 작업 접수 API와 진행 단계를 만들고, 명령 기록·보낼 메시지 목록(outbox)을 저장해요.
  • D10 / E03-04~06: 실제 인계를 확인하고, 취소·보류·재개 절차를 만들어요.
  • D11 / E03-07~08: 작업을 다른 로봇에 넘기거나 일부 실패 뒤 회수·대체하는 절차를 만들어요.
  • D12 / E03-09~10: 장애 뒤 상태를 대조하고, 업무 시스템에 못 보낸 결과를 다시 알려요.
  • D13 / E04-01~03: 가능한 로봇을 고르고, 마감과 오래 기다린 정도를 반영해 기본 배차를 만들어요.
  • D14 / E04-04~06: 생산순서 변경, 충전, 목적지 불능에 대응해요.
  • D15 / E04-07~08: 계속 밀리는 작업을 찾아내고, 승인된 사람이 우선순위를 바꾸게 해요.
  • D16 / E04-09~10: 실제 명령 없이 배차안을 비교하는 shadow 시험 후, 검증된 정책만 제한 적용해요.

공장 실행: robot-platform-stories-factory

  • D17 / E05-01~03: 구역 사용을 예약하고, 진입·실제 점유·이탈을 확인해요.
  • D18 / E05-04~06: 교차로 순서, 서로 기다리는 교착, 공사 때 통로 폐쇄를 처리해요.
  • D19 / E05-07~08: 충전기·인계점을 관리하고, 설비와 준비·완료 신호를 주고받아요(handshake).
  • D20 / E05-09~10: 구역이 바뀔 때 제어권을 넘기고, 자유주행 로봇의 실제 경로를 확인해요.
  • D21 / E06-01~03: 생산(MES)·창고(WMS)·품질(QMS) 시스템의 사건과 기준 기록을 연결해요.
  • D22 / E06-04~06: 부품·용기·제품을 연결하고, 인계를 확인한 뒤 재고에 반영해요.
  • D23 / E06-07~08: 마감 변경과 품질 보류품의 이동을 처리해요.
  • D24 / E06-09~10: 결과 재전송, 기록이 안 맞는 작업 목록, 오래된 시스템과의 연결을 만들어요.
  • D25 / E07-01~03: 지도, 작업 진행 이력, 알람으로 현재 상황을 보여 줘요.
  • D26 / E07-04~06: 복구 순서를 안내하고 수동 조작·교대 때 책임을 넘겨요.
  • D27 / E07-07~08: 작업자의 물품 인계 화면과 설정 변경 전 영향 확인 화면을 만들어요.
  • D28 / E07-09~10: 운영 보고서와 다국어·접근성 지원을 준비해요.
  • D29 / E08-01~03: 현장 서버를 배치하고, 이중 명령을 막고, 저장한 기록을 복원해요.
  • D30 / E08-04~06: 중앙과의 광역망(WAN) 단절, 무선 품질 저하, 과부하를 분리해 대응해요.
  • D31 / E08-07~08: 일부부터 업데이트하고, 장비 시계가 어긋나는지 확인해요.
  • D32 / E08-09~10: 서버 손실 복구 훈련을 하고, 어떤 부하까지 시험했는지 정리해요.

통제·확장: robot-platform-stories-assurance

  • D33 / E09-01~03: 사람의 신원·역할 권한과 장비의 인증서를 관리해요.
  • D34 / E09-04~06: 메시지/API 접근 허용 목록(ACL), 공급사 접속 승인, 조작 이력을 관리해요.
  • D35 / E09-07~08: 비밀키를 교체하고, 취약점과 소프트웨어 구성 목록(SBOM)을 확인해요.
  • D36 / E09-09~10: 로그·영상은 필요한 만큼만 모으고 보안사고 대응을 준비해요.
  • D37 / E10-01~03: 위험 목록, 안전 장치의 책임, 정지·수동 상태의 뜻을 정리해요.
  • D38 / E10-04~06: 재개 승인, 변경 후 위험 재검토, 정비 작업 절차를 연결해요.
  • D39 / E10-07~08: 구역 제한을 검증하고 안전 시험의 근거를 남겨요.
  • D40 / E10-09~10: 비상상황을 훈련하고 안전 운영 책임을 인수해요.
  • D41 / E11-01~03: 통신 약속 시험, 기록된 물류 재생, 실제 하드웨어를 연결한 시험(HIL)을 준비해요.
  • D42 / E11-04~06: 일부러 장애·높은 부하를 만들고, 오래 돌려 보고, 기존 기능도 다시 시험해요.
  • D43 / E11-07~08: 같은 소스·의존성·조건으로 빌드를 재현하고 추적할 수 있게 해요. 독립 시험 구역의 인수 조건도 갖춰요.
  • D44 / E11-09~10: 소규모 배포·되돌리기와 공급사 변경 후 재시험을 준비해요.
  • D45 / E12-01~03: 기록의 뜻을 맞추고, 성과 지표(KPI)와 막히는 원인을 분석해요.
  • D46 / E12-04~06: 총소유비용(TCO)과 정비 기록을 분석하고 시뮬레이션을 실제 결과에 맞춰요.
  • D47 / E12-07~08: 공장별 데이터·권한을 구분하고 검증된 설정을 재사용해요.
  • D48 / E12-09~10: 조회만 가능한 AI 지원과 승인받은 최적화 실험을 준비해요.

우선순위와 완료의 의미

모든 기능을 동시에 만들지는 않아요. 우선순위는 다음처럼 읽으면 돼요. M은 착수 후 개월, Y는 착수 후 연차입니다.

  • P0: 첫 생산 시험 운영 전에 있어야 하는 기능과 통제예요. M1~M12 안에 완료하는 계획이에요.
  • P1: 실제 운영을 안정화하고 첫 2년 목표를 채우는 기능이에요. M13~M24가 목표예요.
  • P2: 3~5년차의 확장 후보예요. 필요한 준비와 효과가 확인되지 않으면 시작하지 않아요.

P0는 70개, P1은 38개, P2는 12개예요. 첫 2년의 P0+P1은 108개지만, 스토리 개수는 개발 인력이나 작업량과 같지 않아요. 장비 접근권과 팀 역량을 확인한 뒤 규모·순서를 다시 추정하고 필요하면 범위나 기간을 조정해야 해요.

스토리의 M6는 “6개월째에 시작”이 아니라 “6개월 안에 검증까지 끝내려는 목표”예요. 보안·안전의 기본 권한과 검토는 P0부터 갖추고 뒤에서 고도화해요. 파일럿에서 항목을 빼려면 왜 필요 없는지 근거를 제시하고 현장·안전·제품 책임자의 변경 승인을 받아야 합니다.

**완료 기준(DoD)**도 코드 작성으로 끝나지 않아요. 코드·설정 검토, 연결 약속 시험, 기존 기능 재시험, 권한 없는 요청의 거부 시험, 장애·복구 영향 확인이 필요해요. 지표·로그·운영 안내·되돌리는 방법과 책임자 승인도 있어야 합니다. 안전 관련 항목은 자격을 갖춘 담당자의 현장 평가를 추가해요. 단위시험 통과가 현장 안전 검증을 대신할 수는 없어요.

자체 개발·재사용·구매 경계

  • 직접 책임질 것: 작업의 뜻, 실제 물품 인계의 완료 조건, 복구 순서, 운영 화면·절차와 공장별 설정 약속이에요. 우리 제품의 핵심이 되는 부분이죠.
  • 검증해서 재사용할 것: Open-RMF 같은 조정 기반[10], 데이터베이스, 메시지를 중계하는 브로커, 관측 도구, 신원 확인 시스템이에요. 사용권, 보안 지원 기간, 업데이트와 현장 유지보수 가능성을 비교해요.
  • 공급사에 남길 것: 로봇 내부 주행·기구 제어, 인증된 안전 기능, 제조사 고유 진단이에요. 대신 연결 방법과 지원 수준인 SLA는 계약으로 확보해야 해요.

VDA 3.0.0 릴리스에는 자유주행 지원과 기존 구현을 그대로 쓸 수 없게 하는 파라미터 변경(breaking change)이 명시돼 있어요.[8] 그래서 무조건 높은 버전을 요구하기보다 대상 장비의 2.x/3.x 지원 구성을 나눠 시험하고 지원표를 내는 편을 권해요. 공식 기준인 규범 PDF와 메시지 형식인 schema를 대조하는 일도 구현 전에 해야 합니다.

조직·비용·일정 산정

현장·제품 분석, 핵심 서버·장비 연동, 제조 IT, 화면·사용 경험(UX), 플랫폼·안정성(SRE), 시험(QA), 보안, 안전·현장 설비(OT) 전문가 역할이 필요해요. 역할이 많다고 그만큼 전담 인원이 확정됐다는 뜻은 아니에요. 지금 단계에서 인원이나 총액을 단정하지는 않습니다. 장비나 API를 못 쓰는 상태라면 개발자를 더 투입해도 현장 시험이 빨라지지 않아요.

M3까지 패키지별로 잘 풀릴 때·보통일 때·어려울 때의 인월을 추정해요. 인월은 사람이 한 달 동안 투입하는 작업량 단위예요. 비용에는 개발 인월×단가 + 장비·시험장 + 공급사 라이선스·지원 + 현장 연결·안전 검증 + 운영 인프라·지원 + 재시험 예비비를 넣어요.

효과도 조심해서 계산해야 해요. 물류 인력이 실제로 어떤 일로 재배치됐는지, 관제 때문에 생긴 대기가 줄었는지, 유지보수비가 바뀌었는지를 나눠 봐요. 생산 증가와 인건비 절감을 같은 효과에 대해 두 번 더하면 안 됩니다.

위험과 미해결 항목

일정을 흔드는 큰 요인은 API 접근 제한, 제조사마다 다른 오류·취소 의미, 지도와 실제 현장의 차이, 안전 검증 지연이에요. 이런 결정은 ADR, 즉 ‘어떤 설계를 왜 골랐는지 남기는 기록’에 적어 두세요. 제어 방식, 기준 기록, 지도·시각의 약속, 명령 주체, 복구, 통신 버전, 배포 방식, 직접 만들지 구매할지를 남기면 다음 담당자가 이유를 알 수 있어요.
