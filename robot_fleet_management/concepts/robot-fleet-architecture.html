로봇 관제 참조 아키텍처

정의와 범위

설명을 위한 상황: 창고에서 물품을 옮기는 로봇과 복도를 청소하는 로봇이 같은 좁은 통로를 쓰려 한다. 각각 목적지까지 움직일 수 있더라도, 어느 작업을 먼저 진행할지와 다른 로봇이 어디에서 기다릴지는 함께 정해야 한다. 이 문서는 그 조정 책임을 어느 시스템에 둘지 설명한다.

이 위키에서 관제(Fleet Management)는 개별 로봇의 모터 제어가 아니라 여러 로봇의 임무·상태·공유 공간을 조정하는 상위 시스템을 뜻한다. 작업 배차 담당자가 할 일과 현장에서 로봇이 할 일을 나누는 구조로 이해하면 된다. 여기서 fleet은 함께 관리하는 로봇 집단이다.

초기 분석 대상은 실내 AMR(Autonomous Mobile Robot, 자율 이동 로봇)과 AGV(Automated Guided Vehicle, 무인 운반차)다. 아래는 구조를 읽기 위한 용어 풀이이며 장비의 기능·안전 등급을 판정하는 분류가 아니다. 약어만 보고 특정 로봇이 경로 변경이나 단절 후 운행을 지원한다고 판단하지 않는다.

  • AMR·AGV: 이 문서에서는 현장에서 이동 작업을 실행하는 로봇을 가리킨다. 실제로 맡길 수 있는 동작은 제조사별로 확인한다.
  • WMS(Warehouse Management System, 창고 관리 시스템): 재고·입출고 등의 창고 업무를 관리하는 상위 시스템이다. 아래 설계에서는 운반 요청을 내는 주체로 둔다.
  • MES(Manufacturing Execution System, 제조 실행 시스템): 생산 현장의 작업 진행을 관리하는 상위 시스템이다. 아래 설계에서는 생산에 필요한 자재 이동 등을 요청하는 주체로 둔다.
  • adapter(어댑터): 관제와 장비 사이의 “통역 계층”이다. 이 문서의 설계에서는 명령·상태뿐 아니라 위치를 나타내는 좌표계와 지도 버전의 의미도 맞춘다. 연결만 되었다고 의미까지 일치하는 것은 아니다.

읽는 범위: 아래 구조는 보존 원문을 바탕으로 정리한 참조 설계이며 특정 제품의 구현도나 인증된 안전 절차가 아니다. 실외·드론 관제로 그대로 일반화하지 않는다. 편집 기준일(updated/as_of)은 2026-10-01이다. 기존 원문과 설명을 대조했으며 외부 원문 재조사나 최신 버전 검증은 하지 않았다. 출처 확인일은 2026-09-14로 유지한다.

확인된 사실

어떤 책임을 나눌지 이해하려면 다음 두 기술의 역할부터 구별하는 편이 좋다.

  • RMF: ROS 2라는 로봇 소프트웨어 기반 위에서, 서로 다른 종류의 로봇 집단이 함께 동작하도록 돕는 라이브러리와 도구의 모음으로 소개된다.[1] 문·승강기·통로 같은 공유 인프라의 조정도 다룬다.[1]
  • VDA 5050: 이동 로봇 집단과 중앙 관제(fleet control) 사이의 통신을 위한 공개 표준으로 소개된다.[2]

따라서 “여러 로봇과 자원을 어떻게 조정할까”를 다루는 프레임워크와 “관제·로봇 사이에서 어떻게 통신할까”를 다루는 표준은 같은 계층의 대체재가 아니다라는 것이 이 위키의 해석이다. 함께 사용하려는 경우에도 실제 연결 방식과 지원 범위를 별도로 검증해야 한다.

자료의 시점과 권위에 주의한다. RMF 입문서는 본문에서 ROS 2 Foxy 시점을 언급하는 역사적 자료다.[1] 여기서는 Open-RMF의 설계 배경과 역할을 설명하는 근거로만 사용하며, 현재 배포판의 API·기능 목록·성능을 보장하는 근거로 쓰지 않는다. VDA 5050 보존 README의 표기는 Version 3.0.0이며, GitHub 문서·JSON schema와 VDA 발행 문서가 다르면 VDA 웹사이트의 PDF가 유효하다고 명시한다.[2] 이 페이지는 README의 소개 범위를 넘어 메시지별 호환성을 확인한 문서가 아니다.

참조 구조 — 설계 제안

한 번의 운반 요청을 업무 요청 → 임무 접수·기록 → 작업·공간 조정 → 장비별 변환 → 현장 실행으로 나눈다. 반대로 현장에서 올라오는 상태는 같은 경계를 거쳐 관제와 업무 시스템에 돌아온다. 다음 표는 권장 책임 분리이며 모든 제품이 이 구조를 갖춘다는 뜻은 아니다.

주체받는 입력맡을 행동남기거나 돌려줄 결과
업무 시스템 또는 요청자운반·생산·서비스상의 필요무엇을 어디로 옮길지, 우선순위·취소 권한·완료 조건을 정한다.식별 가능한 작업 요청과 완료 기준
임무 API와 작업 상태 저장소업무 요청과 진행 보고API(프로그램 간 호출 창구)로 요청을 받고, 임무 ID를 부여해 진행 상태를 저장한다.접수 기록, 미완료 임무 목록, 완료 여부
관제의 작업·교통 조정 기능미완료 임무, 로봇 상태, 통로·설비의 사용 상태어느 로봇에 일을 맡길지와 공유 자원을 누가 언제 쓸지 조정한다. 장애 뒤에는 할당과 점유 상태를 다시 맞춘다.작업 할당, 자원 사용 계획, 재조정 기록
로봇별 adapter관제 지시 또는 로봇의 상태·오류 보고제조사별 명령·상태의 의미와 좌표계·지도 버전을 맞춘다.로봇이 이해할 지시, 관제가 해석할 상태·오류
로봇의 주행·제어 기능지원하는 범위의 지시와 현장 감지 정보현장 이동을 실행하고 진행 상태를 보고한다. 감지·정지 책임은 별도 위험 분석으로 확정한다.수신·실행·물리적 완료 상태와 현장 오류
문·승강기·충전기용 자원 adapter자원 사용 요청과 설비 상태별도 설비 인터페이스를 통해 사용 요청·상태를 연결한다.관제가 판단에 쓸 설비 상태와 요청 결과

운영 화면(UI)·감사 로그·지표 수집은 어느 한 계층의 성공 메시지만 보지 않고 전체 흐름을 추적하도록 설계한다. 예를 들어 “임무가 접수됨”과 “로봇이 물품을 인계함”을 같은 완료로 표시하지 않는다. 누가 요청·취소했고 어느 단계에서 멈췄는지 임무 ID로 연결해 볼 수 있어야 한다.

작업 하나를 끝까지 따라가 보기

다음은 책임 분리를 설명하기 위한 가상 사례이며, 실제 구현·실험 결과가 아니다. WMS가 “보관 구역의 물품을 포장 구역으로 옮겨 달라”고 요청하고, 도중에 청소 로봇과 통로를 공유한다고 가정한다.

  1. 업무 시스템이 완료 조건을 정한다. 목적지 도착만으로 끝낼지, 물품 인계 확인까지 필요할지를 요청에 명시한다. 임무 API는 이를 접수하고 임무 ID와 함께 저장한다.
  2. 관제가 작업과 통로 사용을 조정한다. 로봇 상태를 보고 운반 작업을 맡긴다. 청소 로봇도 같은 통로를 쓸 예정이라면 우선순위와 현장 제약에 맞춰 대기·통과 순서를 계획한다. 이 계획 자체가 안전한 통과를 보장하는 것은 아니다.
  3. adapter가 지시의 의미를 맞춘다. 관제의 “포장 구역”이 로봇 지도에서 어느 위치인지 확인하고 장비가 지원하는 지시로 변환한다. 문을 통과해야 한다면 문용 adapter를 통해 설비 상태도 확인하도록 설계한다.
  4. 로봇과 관제가 진행 상태를 나누어 기록한다. 로봇이 명령을 받았다는 보고, 이동을 시작했다는 보고, 물리적으로 목적지에 도착했다는 보고를 구분한다. 완료 응답이 없다는 이유만으로 같은 운반을 다시 지시하지 않는다.
  5. 정해 둔 업무 조건으로 완료를 판정한다. 인계 확인까지 요구했다면 도착 기록만으로 완료 처리하지 않는다. 완료 조건을 확인한 뒤 업무 시스템에 결과를 돌려준다.

이 흐름에서 관제는 작업 간 충돌과 상태 불일치를 조정한다. 로봇의 실제 감지·정지 기능, 설비 제어, 업무 완료 판정까지 하나의 “명령 전송 성공”으로 대신하지 않는다.

Trade-off와 실패 모드

중앙 조정은 전체 작업을 함께 보고 최적화하기 쉽지만, 중앙 장애나 늦게 도착한 상태를 고려해야 한다. 반대로 로봇 자율성을 높이면 통신 단절 대응 여지가 커지지만 관제의 계획과 실제 움직임이 달라질 수 있다. 이는 설계상 추론이지 특정 구현의 성능 보장이 아니다.

실패 상황생길 수 있는 오해설계·시험에서 확인할 항목
로봇 상태가 늦게 도착함마지막 위치를 현재 위치로 취급함상태의 관측 시각·수신 시각과 오래된 상태의 처리 규칙
adapter의 지도·좌표 해석이 다름같은 목적지 이름이면 같은 위치라고 생각함지도 버전과 좌표 변환을 장비 양쪽에서 대조
완료 응답 유실 또는 관제 재시작아직 실행하지 않았다고 판단해 같은 작업을 재지시함명령 수신·동작 시작·물리적 완료를 분리한 기록과 중복 실행 방지 정책
자원 사용 기록과 현장이 어긋남통로·설비를 쓸 수 있다고 잘못 판단함실제 상태 확인과 장애 후 할당·자원 점유 재조정

통신이 복구됐다는 이유만으로 운행을 재개하지 않는다. 미완료 임무와 실제 로봇 상태를 대조하는 설계는 fleet-communication-and-recovery에서 이어서 설명한다.

검증과 미해결 질문

첫 PoC(개념 검증 시험) 전에 업무 시스템·관제·로봇·설비 담당자가 다음을 인터페이스 계약으로 작성하는 것을 제안한다. 여기서 계약은 각 구성 요소가 주고받을 값과 책임을 합의한 문서다.

  • 제어 범위: 어떤 명령을 지원하며 “정지”, “취소”, “재개”가 각각 무엇을 뜻하는가?
  • 위치와 작업 소유권: 지도·좌표를 어떻게 변환하며, 임무별로 누가 명령을 내리고 완료를 판정할 권한이 있는가?
  • 단절·재시작: 통신이 없을 때 허용할 행동은 무엇이며, 어떤 기록과 현장 확인을 거쳐 재개할 것인가?

안전 경계: 관제의 교통 계획이나 통신 규격 지원은 안전 인증이 아니다. 로봇의 감지·정지 책임, 단절 시 허용 행동, 운행 재개 조건은 별도 위험 분석과 적용 법규·규격 검토로 확정해야 한다. 이 문서로 정지 거리나 안전 등급을 보장하지 않는다.

보안 경계: 누가 명령을 보낼 수 있는지 확인하는 신원 인증, 허용할 명령을 정하는 인가, 키·자격 증명 관리도 따로 설계·검증해야 한다. 위의 adapter와 관제 구조만으로 이 기능들이 제공된다고 가정하지 않는다. 안전·운영 통제는 fleet-safety-and-operations를 참고한다.

아직 확인하지 않은 것: 대상 제조사·로봇 수·건물 구조가 정해지지 않았다. 최신 Open-RMF 구현, VDA 5050 규범 PDF·메시지별 지원, 장비 간 호환성, 현장 처리량·복구 시간, 안전·보안 적합성은 이번 편집에서 검증하지 않았다. 도입 시험 항목은 fleet-evaluation-checklist에서 구체화한다.
