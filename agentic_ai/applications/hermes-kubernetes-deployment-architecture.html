Hermes Agent Kubernetes 배포 아키텍처

한눈에 보기

Hermes Agent는 공식 Docker 이미지와 Gateway/API Server를 제공하므로 Kubernetes에서 실행할 수 있다. 그러나 /opt/data에 config, credential, session, skill, memory를 보존하고 Responses API가 서버 측 대화 상태를 유지하므로, 단일 공유 볼륨을 여러 replica가 동시에 사용하는 stateless Deployment로 취급하면 안 된다.Hermes Docker Hermes API Server

권장 기본형은 프로필 또는 shard별 단일 writer StatefulSet + 독립 PVC + ClusterIP Service다. 외부 Ingress는 Agent Gateway만 노출하고 Hermes Service는 cluster 내부에 둔다.

왜 StatefulSet인가

Hermes 공식 컨테이너는 모든 사용자 데이터를 /opt/data에 마운트하고 이미지 자체는 stateless하게 교체할 수 있도록 설계됐다. API Server와 health endpoint는 기본적으로 gateway port 8642에 제공되며, non-loopback listen에는 API_SERVER_ENABLED, API_SERVER_HOST=0.0.0.0, 충분히 강한 API_SERVER_KEY가 필요하다.Hermes Docker

Kubernetes StatefulSet은 안정적인 Pod identity와 persistent storage가 필요한 workload를 위해 설계됐고 volumeClaimTemplates로 Pod별 PVC를 만들 수 있다.Kubernetes StatefulSet 이 특성이 Hermes profile/session shard와 맞는다.

Hermes Responses API의 previous_response_id와 named conversation은 서버가 이전 tool call과 결과를 포함한 대화 상태를 저장한다. 따라서 동일 conversation을 상태를 공유하지 않는 임의 replica로 round-robin하면 문맥과 dashboard session history가 갈라질 수 있다.Hermes API Server

수평 확장과 세션 라우팅

Hermes 한 profile을 여러 replica로 복제하는 대신 profile/shard를 늘린다.

Gateway DB는 conversation_id, profile, shard, previous_response_id 또는 named conversation, owner와 lifecycle 상태를 저장한다. 동일 대화는 같은 shard로 보낸다. 장애 시 PVC를 같은 shard identity에 다시 attach해 복구하고, 다른 shard로 이동할 때에는 세션 데이터의 일관된 migration 절차가 필요하다.

Cron과 Slack 같은 messaging gateway를 profile별로 실행한다면 동일 channel/event를 여러 replica가 중복 소비하지 않도록 singleton ownership 또는 leader election을 별도 설계해야 한다. 공식 문서는 Kubernetes leader election을 제공한다고 명시하지 않으므로 자동 HA를 가정하지 않는다.

보안과 운영 통제

  1. Hermes Service는 ClusterIP로 두고 public Ingress를 연결하지 않는다.
  2. 브라우저에는 API_SERVER_KEY와 provider credential을 전달하지 않는다.
  3. Secret은 External Secrets/Vault 등으로 주입하며 Git과 ConfigMap에 넣지 않는다.
  4. automountServiceAccountToken: false, non-root, capability drop, seccomp를 기본으로 한다.
  5. Wiki나 저장소는 필요한 경로만 read-only 또는 작업별 PVC로 mount한다.
  6. terminal/file-write/deploy tool은 별도 profile과 approval policy로 제한한다.
  7. NetworkPolicy로 LLM provider, 허용 웹 목적지와 Gateway 통신만 허용한다.
  8. session, tool call, approval, latency, token, disk pressure를 중앙 로그·trace로 수집한다.

공식 Docker image는 gateway를 s6-overlay로 supervise할 수 있다. Kubernetes도 Pod 재시작을 담당하므로, process supervision과 Pod lifecycle이 함께 작동하는 실제 failure mode를 staging에서 확인해야 한다.Hermes Docker

도입 순서

  1. replicas: 1 StatefulSet, PVC, ClusterIP로 내부 PoC를 만든다.
  2. /health, /v1/responses, SSE, 재시작 후 session 복구를 검증한다.
  3. Website Gateway에서 사용자 ownership과 conversation→shard mapping을 적용한다.
  4. NetworkPolicy, Secret rotation, approval, backup/restore를 검증한다.
  5. 부하가 증가하면 replica 수가 아니라 독립 profile/shard 수를 늘린다.
