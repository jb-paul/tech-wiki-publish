Palantir Foundry Ontology 심층 분석

한눈에 보기

Palantir Foundry Ontology는 기업 데이터를 업무 객체로 정규화하고 관계·행동·코드 로직·권한을 하나의 실행 계층에 결합한 operational ontology다.

전통적인 OWL/RDF 지식표현 언어의 구현체라기보다 Palantir 플랫폼에 종속된 운영 의미 계층에 가깝다. Palantir는 이를 조직의 digital twin으로 설명하며, 데이터셋과 모델을 object type, property, link type, action type으로 매핑한다.Core concepts

핵심 차별점은 명사형 의미 모델만 제공하지 않는다는 것이다.

Palantir 공식 아키텍처는 이를 data + logic + action + security의 통합으로 설명한다. 즉 ontology가 데이터를 설명하는 schema에 머무르지 않고, 조직이 어떤 상태를 읽고 어떤 변경을 허용하는지를 운영 계약으로 만든다.Ontology system

다만 “Ontology를 자동 생성한다”는 의미로 평가하면 자동화 수준은 중간 정도다. 데이터 열을 property로 자동 매핑하고 metadata·API name·표준 편집 action을 생성하며, Pipeline Builder와 Palantir MCP로 구조 생성을 자동화할 수 있다. 반면 어떤 업무 개념을 object로 만들지, relation의 의미와 방향, canonical identity, scope, 권한 및 action semantics를 자율적으로 발견·승인하는 end-to-end ontology learning은 공식 문서에서 확인되지 않았다.

1. Palantir가 말하는 Ontology의 구성

1.1 Object type과 object

Object type은 현실의 entity 또는 event에 대한 schema이고 object는 그 instance다. 데이터셋에 비유하면 object type은 dataset, object는 row, property는 column, link type은 join과 대응한다.Core concepts

이 비유는 초기 이해에는 유용하지만 Palantir Ontology가 단순 ORM이라는 뜻은 아니다. 동일 object type에는 rich metadata, application view, action, function, security policy와 writeback 동작이 연결된다.

1.2 Property와 shared property

Property는 object의 특성을 정의한다. Shared property는 여러 object type에서 공통으로 사용하는 property metadata를 중앙 관리한다. 데이터 열과 자동 매핑할 수 있지만 안정적인 ID, API name, type, description, owner, primary/title key를 정하는 것은 설계 책임으로 남는다.

1.3 Link type

Link type은 두 object type 사이 관계의 schema다. 실제 link는 두 object instance 사이의 관계다. 데이터 join에서 출발할 수 있지만 업무적으로는 relation 이름, 방향, cardinality, identity와 갱신 책임을 결정해야 한다.

예를 들어 WorkOrder AFFECTS Equipment와 Equipment HAS_WORK_ORDER WorkOrder는 탐색 방향과 사용자 표현이 다르다. 단순히 동일 키를 가진 열을 발견하는 것만으로 적절한 relation semantics가 자동 결정되지는 않는다.

1.4 Action type

Action type은 object, property value, link에 한 번에 적용할 변경과 side effect를 정의한다. 예를 들어 Assign Employee는 role property 변경, 새 manager link 생성, 알림 전송, 실행 권한 검사를 하나의 transaction에 묶을 수 있다.Action types

이것이 Palantir Ontology가 전통적 semantic model과 가장 크게 갈리는 부분이다. Object가 명사라면 Action은 허용된 동사이며, ontology가 읽기 모델과 command surface를 함께 제공한다.

1.5 Function과 automation

Function은 object·object set을 입력으로 받고 property를 읽거나 business logic을 실행하는 code-based logic이다. 단순 rule, ML model, LLM 호출, optimizer, multi-step orchestration이 action과 결합될 수 있다.Core concepts Function의 수정은 Ontology Manager가 아니라 Functions Code Repository에서 이뤄지고 version·usage·observability가 별도로 관리된다.Ontology Manager

1.6 Interface

Interface는 object type의 shape와 capability를 정의하여 여러 object type에 polymorphism을 제공한다. 서로 다른 객체가 공통 property·capability 계약을 구현하게 해 application과 agent가 구체 type에 덜 의존하도록 한다.

2. 온톨로지를 만드는 실제 절차

2.1 Ontology Manager 중심의 GUI 방식

Ontology Manager는 object type, link type, action type을 만들고 datasource를 연결하며 indexing·application 반영 상태를 조사하는 관리 도구다.Ontology Manager

대표적인 object type 생성 흐름은 다음과 같다.

  1. 업무 use case와 object 후보를 정한다.
  2. Foundry dataset·virtual table 등 backing datasource를 선택한다.
  3. wizard가 metadata와 property 후보를 채운다.
  4. primary key와 title key를 지정한다.
  5. 필요 없는 column/property를 제거하고 이름·설명을 정제한다.
  6. object 사이 link type을 정의한다.
  7. 표준 편집 action을 선택적으로 생성한다.
  8. project와 permission을 지정한다.
  9. 변경을 staging하고 검토한 뒤 main 또는 branch에 저장한다.
  10. indexing과 downstream application 동작을 확인한다.

2.2 Datasource 기반 bootstrapping

기존 datasource를 선택하면 wizard가 다음을 자동화한다.Create an object type

  • object type metadata 초기화
  • 모든 column을 property로 매핑
  • column 이름으로 property ID·display name·base type 추론
  • display name에서 object/property API name 추론
  • 선택적으로 표준 edit action 생성

수동 편집 화면에서도 Add all unmapped columns as new properties로 남은 열을 일괄 property로 만들 수 있다. Struct property는 Automap all을 통해 모든 하위 column을 자동 매핑할 수 있다.Struct automapping

이 기능은 schema bootstrapping에는 강하지만 semantic conceptualization은 아니다. 소스 열의 이름과 base type으로 초안을 만들 뿐, 다음 판단은 builder가 담당한다.

  • row가 entity인지 event인지
  • 어떤 source가 authoritative system of record인지
  • business identity와 primary key가 무엇인지
  • 동일 개념을 merge할지 분리할지
  • relation의 의미·방향·cardinality가 무엇인지
  • status를 property로 둘지 별도 object로 만들지
  • action이 허용할 상태 전이와 side effect가 무엇인지

2.3 Pipeline Builder 방식

Pipeline Builder는 batch와 streaming dataset에서 object와 link output을 만들 수 있다. output guidance를 먼저 선언하여 pipeline이 목표 ontology 구조에 맞는 데이터를 생성하도록 설계할 수 있다.Add an Ontology output

하지만 streaming-backed object에서는 Pipeline Builder로 edit를 활성화하거나 many-to-many link를 구성할 수 없는 제한이 공식 문서에 명시돼 있다. 따라서 ingestion 자동화 범위와 operational write model의 범위를 구분해야 한다.

2.4 Ontology-as-code와 import/export

Object type은 SuperRepo에서 Ontology-as-code로 정의할 수 있으며, Ontology Manager에서 만든 object type도 SuperRepo로 가져올 수 있다.Create an object type

Ontology Manager의 working state는 JSON으로 export하여 code/text editor에서 수정하고 다시 import할 수 있다. 그러나 Palantir는 exported JSON schema가 시간에 따라 바뀔 수 있으므로 의존하지 말라고 명시한다. Conditional formatting rule 등 일부 artifact는 다른 ontology로 이동하지 못할 수 있다.Export/import

따라서 JSON export는 편집·복제 수단이지 안정적인 W3C 교환 표준이나 vendor-neutral ontology artifact로 간주하면 안 된다.

3.2 Palantir MCP와 AI 지원

공식 문서는 두 MCP 계층을 구분한다.Ontology MCP

  • Ontology MCP: ontology 소비자인 외부 agent가 object를 읽고, query function을 호출하며, 미리 정의된 action을 실행하도록 노출한다. Application restriction과 permission으로 실행 범위를 제한한다.
  • Palantir MCP: ontology builder가 dataset, transform, object type, link type, action type 등 구조를 개발·수정하도록 70개 이상의 tool을 제공한다. 실제 production ontology data를 쓰는 도구와는 분리된다.

이는 생성 자동화에 중요한 진전이다. Coding agent가 tool을 조합해 ontology resource를 만들 수 있기 때문이다. 그러나 MCP는 capability surface이지 올바른 ontology를 스스로 발견하는 학습 알고리즘이 아니다. Agent가 만들어도 source-to-concept 근거, identity, modelling quality와 downstream regression은 별도 검토가 필요하다.

4. 관리와 변경 통제

4.1 Working state와 save

Ontology Manager의 변경은 먼저 사용자 로컬 work-in-progress state에 쌓인다. Save 전에 모든 edit, error, warning을 검토하며, error는 저장을 차단하지만 warning은 확인 후 저장할 수 있다. 다른 사용자가 먼저 저장했으면 최신 변경을 update하고 conflict를 해결해야 한다.Save changes

Property ID나 primary key 변경은 application, object edit, link에 파괴적 영향을 줄 수 있다. Palantir 문서는 primary key를 deterministic하게 만들고 중복을 검사하라고 명시한다. 이 점은 ontology evolution이 단순 metadata 편집이 아니라 state migration이라는 것을 보여준다.

4.2 Global Branching과 proposal

Ontology는 Global Branching과 통합되어 별도 branch에서 object, action, link, interface, shared property를 수정할 수 있다. Main 변경을 rebase하고 conflict를 resource 단위로 해결한 뒤 proposal을 만들어 review·merge한다.Branching

Ontology proposal은 Pull Request와 유사하다. Resource별 task, reviewer, approval policy, changelog, branch preview/index 상태를 제공한다.Review proposals

관리 성숙도는 높지만 제한도 있다.

  • ontology 변경이 들어간 branch는 자동 rebase가 아니라 수동 rebase가 필요할 수 있다.
  • backing datasource 삭제·교체와 conditional formatting 충돌은 merge 실패를 유발할 수 있다.
  • Pipeline Builder에서 만든 object type은 branch의 Ontology Manager에서 수정할 수 없다.
  • reviewer 지정이 ontology resource 전체 proposal에 적용되는 구조적 제약이 있다.

4.3 권한 모델

신규 ontology에서는 ontology resource를 Compass project에 파일처럼 저장하고 project role로 view·edit·manage 권한을 정한다.Ontology permissions

중요한 구분은 다음과 같다.

  • Object type 권한: schema와 metadata를 볼 수 있는가
  • Object data 권한: backing datasource 또는 object/property security policy를 통과하는가
  • Link edit: link type과 연결된 양쪽 object type에 edit 권한이 필요한가
  • Action edit/run: action type과 action이 수정하는 모든 resource의 권한을 충족하는가
  • Classification: project classification과 declassification 권한을 충족하는가

이 구조는 ontology가 agent tool registry로 쓰일 때도 중요하다. Tool이 발견된 것과 그 action을 실행할 권한이 있는 것은 별개다.

4.4 관측성과 소비자 영향

Ontology Manager는 action과 function의 usage, version, 최근 실행 지표 및 monitoring rule을 보여준다. Function 소비 application을 찾아 version upgrade를 추적할 수 있다. Branch preview로 object indexing 결과를 production merge 전에 시험할 수도 있다.

이것은 일반적인 ontology editor보다 운영 친화적이다. 반면 OWL reasoner consistency, SHACL conformance, competency question coverage 같은 formal ontology 품질 지표가 중심에 있다는 증거는 공식 문서에서 확인되지 않았다. Palantir의 검증은 주로 platform resource validity, indexing, application compatibility, permission 및 runtime 동작에 초점이 있다.

Palantir의 link type을 OWL object property, object type을 OWL class와 완전히 동일시하면 안 된다. Palantir는 운영 schema와 application contract에 초점을 두며, OWL의 open-world semantics, description logic axiom, 자동 entailment와 같은 기능을 동일하게 제공한다고 공식 문서가 주장하지 않는다.

6. Agentic AI에서의 가치

Palantir Ontology는 agent loop의 다음 지점에 직접 결합된다.

  1. Observe: 원시 datasource를 typed object와 link로 정규화한다.
  2. Retrieve: object set과 query function으로 허용된 업무 context를 선택한다.
  3. Plan: interface·function·action metadata로 가능한 동작을 제한한다.
  4. Act: 미리 정의된 action을 통해 transaction과 side effect를 실행한다.
  5. Verify: action rule, permission, application restriction, runtime monitoring으로 결과를 통제한다.
  6. Audit: 사용자·agent가 수행한 action과 resource version을 운영 기록에 연결한다.

Ontology MCP는 agent가 object, query, action을 MCP tool로 발견하게 한다. 이것은 task-tool-and-capability-ontology의 상용 구현에 가깝다. 특히 agent가 자유 형식 API call을 만드는 대신 승인된 action surface를 호출하게 한다는 점이 안전성에 유리하다.

그러나 ontology 자체가 잘못되면 typed tool도 잘못된 의미를 안정적으로 실행할 수 있다. 따라서 ontology correctness와 action authorization을 혼동하면 안 된다.

7. 강점과 한계

강점

  • 데이터, 의미 모델, application, action, function, 권한을 하나의 운영 계층으로 연결한다.
  • Datasource schema에서 object/property를 빠르게 bootstrap할 수 있다.
  • GUI, Pipeline Builder, Ontology-as-code, SDK, MCP를 함께 제공한다.
  • Branch, proposal, conflict resolution, approval policy로 안전한 변경 흐름을 지원한다.
  • Object/action/function을 agent가 소비할 수 있는 typed tool로 전환한다.
  • Schema 권한과 instance data 권한을 분리하고 project·classification 정책과 결합한다.
  • Application 사용량과 function/action observability를 ontology 관리에 연결한다.

한계와 불확실성

  • 기능과 효과에 관한 공개 근거가 대부분 Palantir 자체 문서이며 독립적인 정량 비교가 부족하다.
  • Ontology라는 명칭이 OWL/RDF ontology와 같은 formal semantics를 제공한다는 뜻은 아니다.
  • 자동화는 schema mapping과 개발 workflow에 강하지만 domain conceptualization의 무인 자동화를 입증하지 않는다.
  • Export JSON schema가 안정적 계약이 아니며 일부 artifact의 cross-ontology import가 제한된다.
  • Platform 전용 object/action/function/security 모델에 깊게 결합되어 vendor-neutral portability가 낮을 수 있다.
  • Runtime validation과 governance는 강하지만 CQ coverage, axiom completeness, independent reasoner 검증은 별도 설계가 필요하다.
  • MCP로 builder automation이 가능해도 hallucinated modelling, 과도한 권한, destructive migration 위험은 사라지지 않는다.
  • 공식 문서는 제품 capability를 설명하지만 구축 기간, steward 인력, 전체 비용, 실패율을 일반화할 근거는 제공하지 않는다.

8. 권장 구축·평가 방법

Palantir 도입 시 “Ontology를 만들 수 있는가?”보다 다음을 검증해야 한다.

Pilot 범위

  • 업무 결정 1개와 competency question 5~10개
  • 핵심 object type 5~15개
  • 중요 link type 10~30개
  • read action과 guarded write action 각각 최소 1개
  • authoritative datasource와 owner 명시

품질 Gate

  1. primary key stability와 duplicate rate
  2. object/entity resolution 정확도
  3. link direction·cardinality 표본 검토
  4. permission on/off 및 data leakage test
  5. branch replay와 downstream application regression
  6. action precondition·side effect·rollback test
  7. Ontology MCP allowlist와 external LLM data exposure 점검
  8. 동일 use case의 ontology on/off task success·latency·운영비 비교

자동화 원칙

최종 판단

Palantir Foundry Ontology는 기업용 operational semantic layer와 action platform을 결합한 높은 완성도의 상용 구현이다. Ontology Manager, Pipeline Builder, branching, project permissioning, OSDK와 MCP를 통해 생성 이후의 운영·배포·agent 연결까지 일관된 toolchain을 제공한다.

하지만 자동 생성 관점의 결론은 제한적으로 봐야 한다.

Palantir는 raw schema를 운영 ontology 초안으로 바꾸고 반복 작업을 자동화하는 능력은 강하지만, domain ontology의 의미를 무인으로 발견·검증하는 완전 자동 생성기는 아니다.

가장 정확한 분류는 human-led semantic design + high automation in mapping, implementation, governance, and agent exposure다. 이는 automatic-ontology-learning-with-llms에서 조사한 LLM 기반 자동 온톨로지 학습과 경쟁한다기보다 상호 보완적이다. LLM은 concept·relation 후보를 제안하고, Palantir는 승인된 모델을 data·action·security·application과 연결해 운영하는 역할에 강하다.
