단일 Agent 아키텍처

한눈에 보기

단일 Agent 아키텍처는 하나의 model policy가 목표, 상태, Tool 목록을 받아 다음 행동을 선택하고 검증 결과에 따라 반복하는 구조다. “프로세스 하나”나 “모델 호출 한 번”을 뜻하지 않으며, planner·memory·verifier·runtime은 별도 모듈이어도 의사결정 주체가 하나면 단일 Agent다.

LLM Agent survey는 profile, memory, planning, action을 포괄하는 통합 구성 관점을 제시한다.Wang et al. 실무에서는 모든 요소를 처음부터 만들기보다 필요한 최소 loop로 시작한다.

핵심 구성과 계약

구성요소책임출력 계약
Goal manager목표·제약·완료 조건 정규화immutable task contract
State store관찰·계획·budget·승인 보존versioned snapshot
Policy/Planner다음 작은 행동 선택action + rationale + expected result
Tool routerschema·권한·timeout 강제typed observation
Verifierpostcondition·완료 판정pass/fail/unknown
Memory검증된 경험 검색provenance가 있는 context
Runtimeretry·checkpoint·cancel·tracedurable state transition

제어 원리

Goal → Observe state → Select action → Policy gate → Execute → Verify → Update → Stop/Replan/Escalate

ReAct는 reasoning과 task-specific action을 교차시켜 외부 관찰로 계획을 갱신하는 패턴을 보였다.ReAct 운영 구현에서는 reasoning 원문보다 action, 근거 링크, observation, verdict를 구조화해 보존하는 편이 감사와 재현에 유리하다.

단계별 구현

  1. 한 도메인과 2~5개 Tool, 명확한 완료 조건으로 범위를 자른다.
  2. read-only Tool부터 schema와 오류 의미를 정의한다.
  3. state machine과 step·시간·비용·retry 상한을 구현한다.
  4. Tool 성공과 task 성공을 분리하는 verifier를 둔다.
  5. 부작용 Tool에는 least privilege, approval, idempotency를 적용한다.
  6. trajectory와 artifact를 저장해 offline evaluation을 반복한다.
  7. 실제 실패가 조정 문제일 때만 multi-agent 분리를 검토한다.

Anthropic은 단순하고 조합 가능한 패턴에서 시작하고, 복잡성이 성능 향상을 정당화할 때 확장하라고 권한다.Anthropic

적용 패턴

  • Tool-using loop: 검색·계산·API 결과를 받아 다음 행동을 수정한다.
  • Plan-and-execute: 계획을 만들되 관찰 후 남은 계획을 다시 검증한다.
  • Evaluator–optimizer: 생성과 평가를 반복하되 외부 완료 조건을 둔다.
  • Guarded operator: read는 자동, write는 proposal과 human gate를 거친다.
  • Stateful worker: 장기 task를 checkpoint에서 재개한다.

장점과 경계

단일 Agent는 shared state와 책임 경계가 명확하고 통신·합의 비용이 적으며 trace를 따라가기 쉽다. 반면 context가 과포화되거나 상충하는 역할을 한 prompt가 맡고, 독립 검증이 필요한 경우 성능이 낮아질 수 있다. 이때도 먼저 context view, specialized Tool, deterministic verifier로 역할을 분리하고, 별도 Agent는 병렬성·격리·독립 판단의 이득이 측정될 때 추가한다.

실패 모드

  • planner의 추측을 observation과 같은 state에 사실로 저장한다.
  • 너무 많은 Tool이 이름·schema 충돌을 일으킨다.
  • 동일 모델의 자기비평을 독립 verifier로 취급한다.
  • 실패 원인을 반영하지 않고 표현만 바꿔 retry한다.
  • memory가 오래되거나 provenance 없는 내용을 다음 task에 주입한다.
  • stop condition이 없어 비용과 부작용이 누적된다.
  • 한 identity에 모든 환경과 action 권한을 부여한다.

운영 고려

  • task success, verifier false pass, step 분포, Tool 오류, 비용, human takeover를 측정한다.
  • state·prompt·model·tool·policy version으로 실행을 재구성 가능하게 한다.
  • context에는 현재 결정에 필요한 최소 view만 넣고 durable state를 별도 보존한다.
  • 같은 state 반복, budget 초과, 상충 evidence는 중단·에스컬레이션 신호로 쓴다.
  • write action 전후 checkpoint와 외부 상태 재확인을 강제한다.
