LLM 기반 Automatic Ontology Generation 연구 지도

한눈에 보기

Automatic Ontology Generation은 자연어 문서·competency question(CQ)·기존 ontology에서 class, relation, hierarchy, constraint, axiom을 추출·설계하고 RDF/OWL 같은 형식으로 직렬화하는 과정을 자동화한다. 다만 현재 연구가 말하는 “자동 생성”은 서로 다른 범위를 포함한다.

  1. 부분 과제 자동화: term typing, taxonomy discovery, relation extraction
  2. 요구사항 기반 draft 생성: user story와 CQ에서 OWL/Turtle 초안 생성
  3. 문서 기반 end-to-end 구성: 문서에서 class/property를 추출하고 hierarchy와 RDF 생성
  4. Ontology+KG 공동 구축: TBox를 만든 뒤 문서 instance를 ABox/KG로 채움
  5. Agentic workflow: 역할 분리, 도구 기반 검증, 수정 loop를 포함한 반자동 공정

가장 일관된 결론은 LLM이 ontology engineer를 대체했다기보다 후보 생성과 초안 작성의 비용을 줄이는 copilot이 되었다는 것이다. 형식 문법 통과, 논리 일관성, CQ 충족, 도메인 적합성은 서로 다른 품질 축이며, 하나를 통과해도 나머지는 보장되지 않는다.Systematic Literature Review

용어와 범위

  • Ontology learning: corpus에서 용어·개념·taxonomy·relation을 학습하는 전통적 연구 범주
  • Ontology generation: 요구사항이나 문서에서 완성도 있는 ontology artifact를 직접 생성하는 접근
  • Ontology extraction: 입력 문서에 명시된 개념·관계를 뽑는 데 초점을 둔 접근
  • Ontology engineering assistance: requirement, conceptualization, encoding, evaluation, documentation, maintenance 중 일부를 지원
  • KG construction: ontology가 정한 schema에 따라 instance와 사실을 채우는 별도 단계

따라서 “triple을 생성했다”거나 “기존 schema로 entity를 추출했다”는 결과만으로 새로운 ontology를 생성했다고 부르면 안 된다. 특히 TBox(class·property·axiom) 생성과 ABox(instance) population을 분리해 평가해야 한다.

연구의 계보

1. 통계·언어 패턴 기반 Ontology Learning

LLM 이전에는 POS tagging, lexico-syntactic pattern, clustering, association rule 등을 이용해 corpus에서 concept와 relation을 추출했다. Text2Onto는 2005년에 여러 학습 알고리즘의 결과를 확률적 ontology model로 축적해 데이터가 바뀔 때 변경을 추적하는 framework를 제안했다.Text2Onto

이 계보가 남긴 핵심 교훈은 다음과 같다.

  • 생성 결과는 단일 정답이 아니라 confidence가 있는 후보다.
  • corpus 변화와 ontology evolution을 연결해야 한다.
  • 사람이 검토할 수 있도록 추출 근거와 변경 영향을 보여줘야 한다.

2. LLM을 부분 과제에 적용: LLMs4OL

LLMs4OL은 ontology learning을 term typing → taxonomy discovery → non-taxonomic relation extraction으로 나눴다.LLMs4OL 2024 Challenge는 WordNet, GeoNames, UMLS, Gene Ontology, DBpedia, FoodOn 등에서 few-shot과 zero-shot을 평가했다.LLMs4OL 2024

중요한 관찰은 다음과 같다.

  • task와 domain별 편차가 매우 크다.
  • biomedical·biological taxonomy와 non-taxonomic relation은 특히 어렵다.
  • fine-tuning, prompt tuning, RAG, rule 결합 중 하나가 보편적으로 우세하지 않았다.
  • zero-shot은 unseen ontology로의 전이를 드러내지만 성능 하락이 컸다.
  • Task C는 가능한 relation 집합을 미리 제공했으므로 완전한 relation 발명 문제는 아니다.

즉 LLMs4OL은 구성요소 benchmark로 중요하지만 end-to-end ontology engineering 전체를 평가하지는 않는다.

3. 요구사항에서 OWL 초안 생성

Navigating Ontology Development with Large Language Models는 ontology story와 CQ를 입력으로 GPT-4가 OWL/Turtle을 생성하도록 하고, novice 학생의 첫·최종 제출물과 비교했다. CQ-by-CQ 방식은 사소한 오류를 제외하면 학생의 첫 제출보다 좋고 최종 제출에 가까웠지만, restriction 생성은 불안정했다.Navigating Ontology Development

이 연구가 보여준 것은 “LLM이 ontology를 안다”라기보다 다음 설계가 효과적이라는 점이다.

  • requirement를 CQ 단위로 분해한다.
  • 이전 artifact를 external memory에 누적한다.
  • 단순 property, reification, restriction을 별도 유형으로 평가한다.
  • 생성된 OWL을 사람이 SPARQL 가능성으로 검토한다.

4. 방법론·도구 검증을 결합한 pipeline

NeOn-GPT는 NeOn 방법론의 requirement specification, conceptualization, implementation을 prompt pipeline으로 바꾸고 RDFLib syntax check → HermiT consistency check → OOPS! pitfall scan → LLM repair를 연결했다.NeOn-GPT

Wine ontology 실험에서는 단순 zero-shot보다 구조가 개선됐지만 gold ontology 대비 class, axiom, individual coverage가 낮고 복잡한 class expression과 property restriction이 부족했다. 이 결과는 validator를 붙이면 오류를 줄일 수 있지만 gold ontology의 개념적 깊이가 자동으로 생기는 것은 아님을 보여준다.

5. Metacognitive prompting과 Ontology Design Pattern

Ontogenia는 CQ, eXtreme Design, Ontology Design Pattern(ODP), metacognitive prompting을 결합했다.Ontogenia 실험에서는 더 많은 axiom과 풍부한 구조가 생성됐지만 다음 오류가 남았다.

  • property hierarchy 부재
  • class/property 혼동
  • 중복 property와 잘못된 domain/range
  • annotation·inverse relation 누락
  • pattern을 잘못 재사용하는 초보자형 modelling error

후속 Ontology Generation using Large Language Models는 10개 ontology, 100개 CQ, 29개 user story에서 Memoryless CQbyCQ와 Ontogenia를 비교하고 structural metric과 expert 평가를 결합했다.Ontology Generation using LLMs 이 계열은 prompt 성능보다 CQ coverage·redundancy·design quality를 다차원으로 보아야 한다는 점을 강화했다.

6. 도메인 corpus에서 relation을 생성

연구 주제 ontology 생성 연구는 IEEE Thesaurus 기반 benchmark로 engineering topic pair의 broader, narrower, same-as 관계를 17개 LLM에 평가했다.Scholarly Ontology Generation 이는 대규모 주제 ontology의 핵심 병목을 pairwise relation classification으로 축소한 접근이다.

Product review에서 meronomy(part-of ontology)를 추출한 연구는 aspect extraction, synset clustering, concept selection, relation extraction의 4단계 pipeline을 사용했다.Meronymic Ontology Extraction 완전 자동화를 주장하지만 평가는 ground truth 대신 LLM-as-a-judge에 의존하고, hallucination을 POS·문자열 필터로 줄였으며, BERT baseline보다 실행 시간이 길었다.

두 연구 모두 좁은 relation vocabulary에서는 유용하지만 OWL constraint와 복합 axiom 생성까지 증명하지는 않는다.

7. Ontology와 KG를 함께 만드는 semi-automatic pipeline

OntoKGen은 RAM·반도체 장비 문서에서 user가 concept, relation, property를 반복 확인한 뒤 KG와 Neo4j Cypher를 생성한다.OntoKGen 최종 ontology에 사용자 선호가 본질적으로 개입하며, 논문 자체도 정량적 CQ 평가는 향후 과제로 남겼다.

Kommineni 등의 pipeline은 CQ 생성 → TBox 생성 → RAG 답변 → KG population → LLM judge를 구성했다.From Human Experts to Machines PROV-O 재사용을 지시했지만 생성 ontology는 기존 class/property 재사용이 제한적이었고, prompt 순서에 따라 KG 결과가 크게 달라졌다. 저자들도 human-in-the-loop 검증을 권고한다.

8. End-to-end와 Multi-agent 접근

OntoEKG는 enterprise text에서 class·property를 추출한 뒤 별도 entailment LLM으로 hierarchy를 만들고 RDF로 직렬화한다.OntoEKG Data·Finance·Logistics 3개 사례에서 fuzzy F1은 각각 0.724, 0.121, 0.431로 편차가 컸다. 주요 실패는 scope 경계, individual/class 혼동, hierarchy 방향 오류, 느슨한 subsumption이었다.

2026년 multi-agent 연구는 보험 계약 문서를 대상으로 Domain Expert, Manager, Coder, Quality Assurer 역할을 artifact 중심으로 분리했다.Multi-Agent Ontology Generation single-agent 대비 structural quality와 queryability가 개선됐지만, 저자 분석상 이득의 핵심은 “agent 수”보다 초기 planning과 명시적 중간 산출물이었다. LLM judge panel과 RAG 평가가 포함되어 결과의 독립성에는 한계가 있다.

공통 Agentic Pipeline

이 pipeline에서 LLM/Agent의 역할은 후보 생성, 분해, 변환, 오류 설명, 수정안 제시다. parser와 reasoner는 문법·논리 오류를 찾고, domain expert는 scope와 현실 의미를 판단하며, CI는 regression을 막는다. LLM이 자신이 생성한 ontology를 단독으로 평가하면 오류 상관관계가 남으므로 독립 도구와 사람이 필요하다.

Agentic AI에서의 사용 지점

자동 생성된 ontology는 agent loop의 다음 단계에 들어갈 수 있다.

  1. Observe: 문서·tool output을 canonical entity와 event type으로 정규화
  2. Retrieve: class, relation, valid-time, provenance 조건으로 memory 후보 제한
  3. Plan: action precondition/effect와 domain constraint로 계획 검증
  4. Act: task-tool-capability relation으로 tool routing
  5. Verify: SHACL/OWL/CQ test로 결과의 구조·논리 검사
  6. Learn: 새 개념을 바로 publish하지 않고 ontology change proposal로 축적

따라서 생성 오류는 ontology-grounded-memory-and-retrieval, ontology-grounded-planning, task-tool-and-capability-ontology에 동시에 전파될 수 있다. 운영 환경에서는 generated ontology에 곧바로 authorization 의미를 부여해서는 안 된다.

평가 설계

1. Element 수준

  • term/class precision, recall, F1
  • taxonomy edge 방향과 transitive reduction 후 비교
  • non-taxonomic relation precision·recall
  • false merge, duplicate, orphan class
  • existing vocabulary/IRI 재사용률

2. Formal 수준

  • RDF/OWL parse success
  • logical consistency와 unsatisfiable class 수
  • domain/range, cardinality, disjointness 위반
  • ODP·SHACL constraint 충족
  • redundant axiom과 unintended entailment

3. Functional 수준

  • CQ를 SPARQL로 표현할 수 있는 비율
  • CQ execution answer correctness
  • downstream retrieval/planning/tool selection 개선
  • unseen document·domain·ontology에 대한 transfer
  • ontology version 변경 후 regression pass rate

4. Human·Operations 수준

  • expert acceptance rate와 수정 시간
  • 처음부터 수작업할 때 대비 절감 시간
  • source span·model·prompt·reviewer provenance coverage
  • 반복 실행 간 stability
  • token·latency·compute cost
  • 잘못 publish된 변경의 rollback 가능성

Systematic review는 30개 논문의 41개 실험을 분석해 task, dataset, metric, workflow가 표준화되지 않았고 pipeline 전체 성능과 LLM component 성능이 자주 혼재한다고 지적했다.Systematic Literature Review 그러므로 논문 간 단일 순위를 만들기보다 같은 input, ontology language, scope, validation tool, CQ set, human budget에서 비교해야 한다.

공통 실패 모드

  • Scope drift: 문서의 모든 명사를 class로 만들거나 필요한 추상화를 놓침
  • TBox/ABox 혼동: individual을 class로, relation을 subclass로 표현
  • Hierarchy inversion: superclass/subclass 방향 반전
  • Vocabulary invention: 기존 표준 IRI 대신 유사한 새 term 생성
  • Domain/range 오류: union 의도에서 여러 domain을 선언해 intersection 의미를 만듦
  • Shallow formalization: label과 subclass만 있고 restriction·axiom이 빈약
  • False consistency: reasoner가 모순을 못 찾았지만 CQ와 도메인 의미는 틀림
  • Repair loop stagnation: 같은 validator 오류를 반복하거나 이전 artifact를 손상
  • Prompt sensitivity: 순서·예시·model version 변화로 구조가 달라짐
  • Self-evaluation bias: 생성 LLM과 judge LLM이 같은 오류와 선호를 공유
  • Provenance loss: 어떤 문장·문서에서 class/relation이 나왔는지 추적 불가
  • Ontology drift: source 변화와 generated ontology version이 분리됨

현재의 결론

  1. 부분 자동화는 실용 단계에 가깝다. term 제안, CQ 생성, class/property 초안, syntax repair, documentation은 유용하다.
  2. end-to-end 무인 생성은 아직 검증되지 않았다. 작은 단일 도메인 demo와 LLM judge 결과를 production readiness로 일반화할 수 없다.
  3. 구조화된 공정이 모델 단독 성능보다 중요하다. CQ, ODP, external memory, parser, reasoner, unit test, review gate가 반복해서 효과를 보였다.
  4. multi-agent의 이점은 역할 수가 아니라 artifact와 검증 경계에서 나온다. planning 없이 여러 agent를 늘리면 비용과 오류 전파만 증가할 수 있다.
  5. ontology는 생성물이 아니라 운영되는 계약이다. version, provenance, ownership, stale knowledge, downstream regression을 포함해야 한다.

열린 연구 문제

  • 문서에서 적절한 ontology scope와 abstraction level을 자동 결정할 수 있는가?
  • class/relation 추출을 넘어 cardinality·temporal·causal constraint를 신뢰성 있게 만들 수 있는가?
  • LLM component와 parser/reasoner/retriever의 기여를 분리한 benchmark를 만들 수 있는가?
  • gold ontology가 유일한 정답이 아닐 때 대안 모델의 semantic adequacy를 어떻게 평가할 것인가?
  • source가 변할 때 ontology diff를 최소·설명 가능하게 생성할 수 있는가?
  • expert correction을 학습하되 승인되지 않은 변경이 자동 publish되지 않게 할 수 있는가?
  • 생성 ontology가 실제 agent task의 성공·안전·비용을 개선하는지 어떻게 입증할 것인가?

상용 운영 플랫폼과의 연결: Palantir

palantir-foundry-ontology는 자동 ontology learning 논문과 다른 층을 담당한다. Palantir는 backing datasource의 column을 object property로 자동 매핑하고 metadata·API name·표준 edit action을 bootstrap하며, Pipeline Builder·Ontology-as-code·Palantir MCP로 구현 작업을 자동화한다. 반면 domain scope, canonical identity, relation semantics, action 권한을 문서에서 자율 발견하고 검증하는 end-to-end ontology generation은 공식 문서에서 확인되지 않았다.

따라서 두 접근의 현실적인 결합은 LLM 기반 concept/relation 후보 생성 → 전문가 승인 → Palantir object/link/action 구현 → branch·proposal·permission·downstream regression이다. Palantir의 강점은 의미 발명보다 승인된 ontology를 data·logic·action·security와 연결해 운영하는 데 있다.
